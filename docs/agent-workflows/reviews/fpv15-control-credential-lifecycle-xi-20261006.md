## Findings requiring implementation before acceptance

1. **P1 — Expired identity cannot be restored by the existing workspace path.** `AuthenticateServiceToken` marks an elapsed identity `status='expired'` (`internal/db/agent_access_store.go`), and the `service_identities_terminal_update_guard` prevents `xinsight_workspace` from changing that terminal status (`migrations/000021_create_connector_installations.up.sql`). The proposed same-identity recovery therefore needs a narrow owner-controlled transaction/function through the existing local controller boundary. It must distinguish time expiry from `status='revoked'`, recheck the original installation, scope, current predecessor, ticket, and authorization under locks, then extend the same identity and activate only the exact replacement. Do not weaken the general trigger or permit revoked identities to return to active.

2. **P1 — The new HTTP paths require explicit auth and dispatch wiring.** `withAccessEnforcement` admits unauthenticated requests only through `isPublicAccessPath`; the proposed cookie-free `resolve` and `recover` paths are absent. Bearer requests are rejected unless `serviceIdentityRoutePermission` grants an exact route; proposed rotate/query/confirm paths are absent. Current `/api/v1/connector-control/installations/` dispatches to setup-only handling. New handlers must register the exact paths, add only resolve/recover to the public transport-checked set, add exact rotate/query/confirm machine routes with the existing poll/ack permissions, and leave all unrelated paths denied. Human recovery creation must retain session, permission, same-origin HTTPS, CSRF, and local controller reauthorization.

3. **P1 — Persist the authoritative current predecessor, not merely a valid token.** The existing XI installation points to one service identity, while `service_identity_tokens` may contain multiple rows and has no connector-current token pointer. During `prepared`, both old and replacement are valid. Normal rotate and expired recovery must compare `previous_token_sha256` against a single durable current digest, and a second distinct operation must conflict. The initial backfill may adopt the sole original token only when the identity and original redeem receipt identify it uniquely; otherwise block with a diagnostic. On confirm, CAS the current digest to replacement and revoke exactly the prior digest. This is required to prevent an older still-valid bearer or a pending replacement from becoming a second lineage.

## Implementability and verified boundaries

- The exact existing invitation/redeem bytes can remain untouched. XI's `service_identity_tokens` supports multiple digests for one identity; UR's binding already stores an encrypted current bearer plus digest/expiry, and `PrepareRedeem` demonstrates durable secret-before-send. XI's work-event renewal demonstrates old-to-new digest replay but has a different permission and lifetime, so it supplies a mechanism rather than a reusable authorization route.
- A committed XI replacement can authenticate query/confirm after the predecessor expires only if XI first extends the active identity's expiry in the same prepare transaction. If XI did not accept before expiry, normal rotate must fail and the two-admin recovery path is necessary. A committed confirm followed by a UR crash is recoverable only if UR retains its encrypted pending replacement until the local current-digest CAS completes.
- The contract correctly treats the old secret plus XI ticket as proof of the original UR installation's custody, not cryptographic proof of a UR human session. UR's own server-side administrator check and transactional recheck are mandatory. XI must verify ticket, old digest, nonrevocation, exact original binding, and scope; no self-reported actor field suffices. Existing terminal revocation after foreign restore must remain terminal.
- `control_fence` and operation ACK are separate from credential generation; no change to their recorded values or history is needed. XI's setup diagnostic may report identity expiry from its own records but must not infer UR's current token from any valid XI token row. The read-only setup/status entrance can expose that condition before `custody_loading`; actual continuity still needs PG, HTTP, UR-loop, Linux, and Target evidence.

## Conclusion

The shared contract is implementable after the three P1 implementation constraints above are made explicit in the frozen version. The review does not certify runtime behavior, PostgreSQL migration, protected-role execution, browser flow, or live deployment; none was exercised for this review.
