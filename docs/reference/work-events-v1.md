# Work events v1 (local implementation slice)

The local receiver exposes `GET /api/v1/work-event-ingest/config` and `POST /api/v1/work-event-ingest/items` over HTTPS to a dedicated `work_event.ingest` service identity. Existing `evidence.read`/`evidence.cite` credentials remain read-only. The root-held administrative store can issue an ingest-only token bound to exact active collections; an optional administrator-paired UR target is returned separately from the reporter scope. The config response carries readable source and project labels, collection revision and scope generation. A POST carries one canonical metadata document plus expected collection revision and generation. Within one PostgreSQL transaction, the workspace role rechecks token and identity validity, exact binding, source and collection status, reporter scope and any registered UR target before immutable admission and audit. A new item returns 201; byte-identical replay returns 200; changed bytes conflict; a missing predecessor remains a retryable dependency. The restricted workspace role has event INSERT and review-body custody grants, without authority to change source registrations or capture policy. The administrator workbench can read active source tuples and explicitly bind each to a new or existing XI project. The managed installation path now registers first-run Agent candidates for administrator approval; optional future-Agent auto-admission is limited to the same approved installation and creates separate XI projects/collections without inferring UR scope. Local synthetic registration and browser tests do not establish a Target credential, installation or route.

`xinsight.work-event.v1` records source-reported agent/tool activity independently of UniRouter requests. A missing model-request relation does not suppress the activity. This local slice provides administrator-registered `agent_runtime` collections, importer and service-token admission, immutable event and relation documents, and authorized workbench list/detail reads. `integrations/openclaw-xinsight` contains a loadable OpenClaw plugin, bounded private metadata SQLite outbox and separate encrypted body outbox. The mapper requires an exact administrator-provided `workspace:<absolute workspaceDir>` or `agent:<agentId>` project binding; missing or changed mappings become visible gaps. Public hook observations may capture bounded input/output and tool bytes after a separate policy and ingest binding; observation failures never change the agent/tool return value. The plugin does not claim OpenClaw hook bytes are the UniRouter network wire. A provider wrapper observes the raw `X-Request-ID` response header for the same model call and can assert a relation only when that exact canonical header and an administrator-paired UR target are present. An isolated synthetic Gateway-to-XI HTTPS/PostgreSQL test covers interleaved calls, 14 work events and three accepted encrypted body copies; it does not establish real UR behavior. Local managed-install/browser tests are described below; they do not establish Target admission or real-provider acceptance. A reported file path remains a source observation, not proof of file contents.

The administrator first registers a distinct active `source_systems` identity with `source_type='agent_runtime'`, then calls `RegisterWorkEventCollection` for its exact `(source_system_id, source_instance, org_id, project_id, scope_generation)` and activates it with the returned revision. One source identity is bound to one `source_instance` and `org_id`; it may contain multiple projects. Registration serializes by source identity and rejects a second instance or organization, including a same-numbered project. Admission rechecks this condition. This makes the existing `source_system_id` plus `project-N` grant namespace unambiguous. This collection is separate from UniRouter `source_fact_streams`. The importer passes the collection's exact revision, generation, status and scope to `CommitWorkEvent` or `CommitWorkEventRelation`. Each transaction locks and rechecks the live registration and source identity; `paused` and `revoked` stop later admission. A revocation is terminal. Collection control is administrator-only and revision-checked.

Event and relation payloads are canonical UTF-8 JSON objects of at most 8192 bytes. Unknown fields, duplicate keys, noncanonical encoding, invalid scope, arbitrary body fields and mismatched reporter scope are rejected. `subject_kind` is `task`, `message`, `model_call`, `tool_call`, or `resource_action`. A task requires `task_ref`; a tool call requires `tool_call_id`; a resource action requires `resource.ref`. `model.requested/completed/failed` requires the source’s actual `model_call_id`, while public `llm_input/llm_output` observations may omit it and remain separate event references. `message.sent_observed` without a native run ID remains a standalone message with no invented task or run reference. Other task/run/model/tool references are optional when the source did not report them. `lifecycle_state` is `started`, `completed`, `failed`, or `unknown`; an action explicitly named `started`, `completed`, or `failed` must agree with it, as must `model.requested` and `tool.invoked` with `started`. A start report cannot be presented as completion. The actor and action kind are typed. The optional resource name may be a path-like locator in the authorized scope; the resource body is never in the event. `content_refs` are typed reference and SHA-256 pairs for user input/output, model input/output, tool input/output, or resource before/after according to subject kind; they never carry inline body bytes. Revisions begin at 1; later revisions require the exact previous event hash. Exact replay is a no-op; changed bytes at the same identity conflict. Relation assertions are separate, may arrive after an event, and bind an exact event revision and hash. They cannot create an event or silently transfer to a later revision. They carry a source-asserted UniRouter target scope and exact `op_…` request ID plus a model-call and evidence reference.

The OpenClaw producer reports `resource.read.failed`, `resource.edit.failed`, and `resource.write.failed` when a corresponding file tool returns an error. These are failed attempts, not file mutations. Its file resource reference includes the bound collection and a lexical path resolved against an observed workspace directory; the readable name retains the tool's original path. Relative paths without an observed workspace directory and URI or home-relative paths are reported as observation gaps instead of being assigned a guessed file identity. Neither the reference nor the readable name proves the physical file or resulting contents.

OpenClaw 2026.9.5 can complete an optional `read` tool call while returning structured `details.kind/status: not_found` for a missing file. XI retains `tool.completed` for the tool outcome and reports `resource.read.not_found` with a failed resource lifecycle only when the structured path matches the observed resource path after resolving either relative path against the observed workspace; it does not claim to have read file contents. If an optional read returns no recognized structured success or absence details, or reports a different path, XI reports `resource.read.unconfirmed` with an unknown resource lifecycle. This classification does not parse the natural-language tool output. Existing immutable event history is not rewritten.

The event's `content_state` and `content_refs` are source assertions about references only. They do not prove byte custody or grant content retrieval. The separate review-body operation proves custody only after exact source, metadata, SHA-256, policy, quota and encryption checks. A human read requires a current `human_review` content grant, verifies the ciphertext and digest before response headers, rechecks authorization while streaming, and records an access audit before bytes leave. A disabled policy blocks new copies without deleting previously accepted bodies; fixed expiry stops reads before the sweeper deletes bytes and releases quota. `XINSIGHT_REVIEW_BODY_KEY_ID` and `XINSIGHT_REVIEW_BODY_KEY_FILE` must be configured together to enable the production server's body route; the file contains 64 hex characters for an independent 32-byte key and is checked as an owner-only, single-link regular file. Without this configuration, the server advertises metadata-only mode. No key or policy has been provisioned outside synthetic tests. Execution-required temporary storage remains a separate purpose, and no UR execution-claim endpoint is used to recover review bytes. The UniRouter C consumer is wired to the importer after an accepted content manifest when a separate XI custody key is configured. Its local PostgreSQL tests cover retry, quota preflight, accepted encrypted copy and fixed expiry; no real UR Target transfer has been run.

`GET /api/v1/work-activity/scopes` discovers the authorized source/project choices. `GET /api/v1/work-activity` lists the latest revision per event in a bounded time window, with optional source, project, exact resource reference or readable resource-name filters and a scope-bound cursor. Filters apply after selecting the latest revision, so an old resource or timestamp cannot reappear as the current activity. `GET /api/v1/work-activity/events/{source_system_id}/{source_instance}/{org_id}/{project_id}/{event_ref}` reads one event. These routes require `workbench.details.read`; list and detail require an active reporter `allow_resource` grant for the project. A relation is only returned when the same subject has an active target UniRouter `allow_source_runtime` grant. `binding_state` distinguishes a relation bound to the current event revision from one bound to a prior revision. `source_asserted_unverified` means the target is still only the reporter's assertion. `ur_identifier_matched` means an independently received UniRouter source-observation row matches the exact target source and request ID; it does not prove tool success, body availability, or file contents.

The work-event migrations are `000041_add_work_events`, `000042_add_review_body_custody` and `000043_add_work_event_install_invites`. Their local PostgreSQL upgrade tests check predecessor-to-43 migration and unchanged existing source/grant rows. The current FPV12 candidate adds `000044_add_managed_connector_adoption` and has runtime schema 44; FPV11/schema43 remains a predecessor. The development schema contract is generated from PostgreSQL 16 after migrations and role grants. Historical release contracts and the existing `resource-action.v1` test-only path remain unchanged. The schema43 qualification does not establish schema44 upgrade qualification or a Target upgrade.


## Managed OpenClaw host installation (local candidate)

The host entry is `integrations/openclaw-xinsight/install.mjs`. This candidate is validated on OpenClaw **2026.9.5** using its native plugin/config commands and public provider `hookAliases`. Other host versions stop with `openclaw_version_not_validated`; passing a package version check alone is not compatibility proof. The managed provider mode selects existing OpenAI-completions/responses providers by the exact administrator-selected UR base URL. It preserves their model catalogs, capabilities, defaults, fallbacks and authentication references. It does not infer a gateway from a provider name or copy model keys into XI. The old `xi-ur-observed` catalog mode remains for existing explicit/synthetic configurations; the installer refuses to silently convert or overlap one.

An XI administrator creates an invitation from the integration screen and supplies the downloaded invitation file to the managed host. Its JSON schema is `xinsight.openclaw-invitation.v1`, with `invitation_id`, `invitation_token`, `origin`, `ur_base_url`, and `expires_at`. The two URLs are exact XI HTTPS origin and UR model API base URL. A host command uses paths only:

```sh
node /path/to/reviewed/openclaw-xinsight/install.mjs \
  --invitation-file /absolute/path/xi-invitation.json \
  --state-dir /absolute/path/private-xi-custody \
  --agent xi-acceptance
```

The caller selects an already reviewed plugin package and a persistent directory outside every Agent workspace. An optional `--openclaw /absolute/path/openclaw` selects the native CLI. The installer validates the full roster from `openclaw agents list --json` and keeps custody outside every Agent workspace. `--agent ID` submits and binds only that roster member as `agent:<ID>`; omit it to submit all discovered Agents. The live plugin also limits later candidate reports to the selected Agent. No workspace or UR affiliation is inferred. The installer narrows only the explicitly selected, current-user-owned invitation file to `0600`, rejects symlinks, and requires its private state directory to be `0700`. The initial handshake supports at most 32 discovered Agents; overflow fails the whole operation visibly instead of dropping Agents. This per-installation bound is not a fleet-capacity claim.

Before the first HTTPS registration request, the host durably creates its own `ingest.key` and independent `body.key` with exclusive creation and `0600` access. A protected `installation.json` binds the invitation, endpoint, package path, original candidate list and optional selected Agent. Rerun with the same `--agent ID` and paths; changing or omitting a frozen selection fails before registration. `POST /api/v1/work-event-install/candidates` sends the invitation, ingest token and candidates; XI stores the credential digest. `POST .../pickup` proves possession of both original values and returns approval state and bindings, never a new secret. Lost replies repeat the same candidate/credential identity. A pending mapping returns `awaiting_administrator` and does not enable the plugin. After the administrator confirms the submitted projects, rerun the same command; it reads the approved configuration with the ingest credential and verifies exact collection and source identity before native configuration changes.

OpenClaw alone updates its configuration and plugin index: a conditional `config set` touches the XI entry, then native `plugins install --link`, `enable`, and `reload` manage the reviewed local package. No whole-config rewrite or model/key migration is performed. Concurrently changed entry values or a different existing plugin source stop setup. Retain the linked package at its reviewed path. A successful native reload returns `activated_waiting_for_events`; it is not evidence that a task or body has arrived. A stopped Gateway or uncertain activation returns `configured_activation_unconfirmed`, leaving the saved configuration for the normal supported Gateway start; the installer does not silently restart a host. XI's actual event/coverage page supplies reception evidence.

To replace the package of an already approved installation, run the reviewed installer with the same invitation file, state directory and `--agent` selection, plus `--upgrade-from /absolute/path/to/current/package`. The installer's own package directory is the target; `--plugin-dir /absolute/path/to/reviewed/package` explicitly selects a different target and requires `--upgrade-from`. The current and target package manifest and `package.json` must match byte-for-byte. Upgrade requires both existing protected keys and validates the saved installation path, native selected source and install record before any native change; it does not create replacement credentials. The installer retains the existing token, body key, Agent mapping, providers and queues. Native `plugins install --link --force --accept-capabilities` may append the target to `plugins.load.paths` while leaving the old source first. After confirming the native install record points to the target, the installer conditionally replaces the old configured path with the target, preserving unrelated paths, then verifies the selected source, calls `enable` and `reload`, checks the selected source and CLI-local `inspect --runtime` import, and atomically records the new package path in the protected installation file. CLI inspection imports the package in that process and does not independently prove what the running Gateway uses; the native reload receipt and subsequent new event evidence remain separate. An uncertain install reply is retried by inspecting the native install record first; an uncertain reload leaves the old saved path and is retried with the same arguments. To roll back after a confirmed upgrade, run the same reviewed installer with `--plugin-dir` set to the retained old package and `--upgrade-from` set to the new package, then verify native reload and the saved path. Keep both immutable package directories until the desired runtime is confirmed. This source migration is not evidence of XI receipt by itself.

`tokenFile` and `bodyKeyFile` are paths, not secret values. The plugin reads them directly with ownership/mode/symlink checks; an invalid configured file never falls back to an environment token. Environment-only legacy/synthetic configuration still has regression coverage. Local file permissions protect against other OS users, not arbitrary code sharing the Gateway's OS principal; stronger host isolation belongs to the managed deployment boundary.

The administrator initially selects discovered Agents with checkboxes and can authorize future Agents for this same installation. A future Agent gets a distinct XI project; its UR scope is never inferred. With future discovery disabled, new candidates wait for an explicit approve/exclude decision; excluded candidates are remembered. The cumulative installation limit includes registered, pending and excluded Agents. The live plugin uses the public current configuration to discover changes and rereads the authoritative ingest configuration after a discovery acknowledgement. The acknowledgement itself is not an admission grant.

Each body capture uses the current collection binding, even in a long-running task. A shared SQLite refresh marker lets hook workers use only recently confirmed body policy. Startup, refresh failure, missing timestamps, clock rollback or expiry of the 60-second freshness interval makes body capture metadata-only; it does not delete accepted history. Explicitly disabled capture is an administrator choice, not an observation failure. Body JSON supports finite numbers and excludes undefined object fields. For `llm_input.tools`, the producer takes only the model-visible `name`, optional `description` and `parameters`; runtime functions are neither executed nor included. This remains a source hook view, distinct from UR wire evidence. The formal Nginx template gives only the exact review-body URL a 32 MiB request-body limit; other paths retain the 8 KiB server limit. The host streams this body to the loopback receiver without Nginx request-body buffering. A 413 is recorded as the fixed `body_too_large` terminal gap, not as a malformed body; it does not identify whether the proxy or application applied the limit.

Managed credentials renew with a prepared owner-only replacement file and an idempotent old-to-new request. Activation requires reading the same installation's configuration with the replacement credential. Identity mismatch stops activation, including recovery from a corrupt pending file; uncertainty does not expand scope. Existing valid credentials remain usable during a failed renewal attempt. Unit and isolated server tests cover these recovery boundaries.

Managed hosts report a bounded snapshot to `POST /api/v1/work-event-install/status` with the existing ingest bearer. The owner resolves the approved installation from the current identity and token; callers cannot choose another installation. The snapshot contains metadata pending/blocked counts, pending body count and ten fixed diagnostic categories. It includes no free-form messages, paths or bodies. The normal refresh loop reports at most once per 60 seconds; a failed diagnostic receipt leaves event delivery active. Repeated snapshots replace the previous counts rather than adding them again.

The administrator installation list includes approved installations even with no future candidates and pages through stable `(created_at, invitation_id)` order. Its detail shows the last server receipt, queues and historical diagnostic occurrences. No report means reception is unconfirmed; a report older than three minutes makes current connectivity unconfirmed. Neither an empty gap list nor a recent receipt proves complete capture. Freshness is display status and does not revoke the installation. HTTP/PG tests cover exact bearer scope, renewal, expiry/revocation and a same-timestamp 22-installation pagination boundary.

A local browser/native CLI/HTTPS/PostgreSQL exercise completed invitation, approval, activation, automatic future-Agent discovery, activity drilldown and verified output-body reading. Its first run exposed an automatic role-grant defect; the synthetic fixture was corrected for diagnosis and a separate fresh-database formal grant regression subsequently passed. The strengthened native Gateway regression then passed with input and output copies both present. Native built-in read/edit/write/read and failed-read steps reached XI, while independent filesystem reads confirmed the edit and final write. The current whole-candidate policy UI and combined integration still require final qualification. These are local synthetic results, not Target or real-provider acceptance.
