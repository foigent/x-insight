# Install and verify X-Insight FPV27

X-Insight FPV27 is an Apache-2.0 development preview for Ubuntu 22.04 and 24.04 amd64 with systemd and dedicated PostgreSQL 16. It uses schema 49 and manual `0.2.0-dev.fpv27/manual-r1`.

## Authenticate this release

Start at the [canonical release](https://github.com/foigent/x-insight/releases/tag/v0.2.0-dev.fpv27). Follow its immutable authority link and verify the publisher, trust store, and download hashes before running the packaged verifier. The release page records the authority commit and the signed application uses product source commit `4d2f53b048f63439fff59f6194946953732ea106` (tree `bd3c86dd7c7d5f7d9832afd36b06b5bb8b04374b`).

The Ed25519 publisher is `ed25519:sha256:765f38f8a4a4f38bf7e94aa3236c28f74dccac56431ab3a1d035a880f6086116`. The signed manifest has source time `2026-11-22T14:11:28Z`. The approved public key interval ends at that exact time and also includes the genuine FPV25 manifest. The verifier checks the signed manifest's source time against the key interval.

## Choose a download route

- **Fresh installation**: download the full signed archive, the raw Linux verifier and the public trust store. Authenticate their bytes against the pinned authority, then run the verifier.
- **Preserving FPV25 upgrade**: start with the exact cached signed FPV25 archive `xinsight-v0.2.0-dev.fpv25-linux-amd64-b77fa1d7cff40a9adafe495d1c4951632819a4d3.tar.gz`. Obtain the six delta assets listed below, including the compressed verifier and trust store if needed. The six file bodies total **12,747,060 bytes**. Verify the old archive and the exact file hashes before reconstruction.

The delta inputs are `delta.json`, `payload.zst`, `release-manifest.json`, `release-manifest.sig`, `xinsight-release-linux-amd64.gz` and `trusted-release-keys.json`. Verify both the compressed download and the raw verifier against the immutable authority record. Extract the verifier to a new path and make it executable after checking its raw hash.

```sh
sha256sum "xinsight-v0.2.0-dev.fpv25-linux-amd64-b77fa1d7cff40a9adafe495d1c4951632819a4d3.tar.gz"
./xinsight-release-linux-amd64-4d2f53b048f63439fff59f6194946953732ea106 materialize-delta \
  --plan ./delta.json --plan-sha256 sha256:a9478ad86d85dddd1f409a109d41864e936ee06a8edae61387be7823e24db332 \
  --basis "/approved/cache/xinsight-v0.2.0-dev.fpv25-linux-amd64-b77fa1d7cff40a9adafe495d1c4951632819a4d3.tar.gz" --patch ./payload.zst \
  --manifest ./release-manifest.json --signature ./release-manifest.sig \
  --trust-store ./trusted-release-keys.json --output "/approved/staging/xinsight-v0.2.0-dev.fpv27-linux-amd64-4d2f53b048f63439fff59f6194946953732ea106.tar.gz"
```

The basis hash is `sha256:ee028acaa06c1f319bc650926a1641e4dac0ba5c6ab129843edb3c3417bdd081`. The output must match the signed FPV27 archive hash below. The materializer refuses a different basis. Use an unused absolute output path.

## Verify, extract and run the native checks

```sh
archive="/approved/staging/xinsight-v0.2.0-dev.fpv27-linux-amd64-4d2f53b048f63439fff59f6194946953732ea106.tar.gz"
./xinsight-release-linux-amd64-4d2f53b048f63439fff59f6194946953732ea106 verify --artifact "$archive" \
  --trust-store ./trusted-release-keys.json --expected-commit 4d2f53b048f63439fff59f6194946953732ea106 --expected-version 0.2.0-dev.fpv27
./xinsight-release-linux-amd64-4d2f53b048f63439fff59f6194946953732ea106 extract --artifact "$archive" \
  --trust-store ./trusted-release-keys.json --expected-commit 4d2f53b048f63439fff59f6194946953732ea106 --expected-version 0.2.0-dev.fpv27 \
  --destination /approved/new-fpv27-staging
```

For new installation, use the [packaged installation and first-owner guide](../getting-started.md) for the host roles, PostgreSQL, TLS, native checks and normal account activation. Read the FPV27 manual from the extracted package for the precise release requirements.

For an upgrade, first preserve the existing installation, database and trust-store identities and complete the native private backup and isolated restore check. The installed trust store must accept the verified publisher and signed time. Run the staged controller's `upgrade --check --artifact "$archive"`; proceed with the approved maintenance and normal `upgrade` when all checks pass. Confirm installed version, schema, readiness, data and existing access from their respective entry points.
