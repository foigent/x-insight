手册使用说明

本手册只适用于与其一同签名发布的 X-Insight 0.3.0-rc.13，手册版本为 0.3.0-rc.13/manual-r13。先核对发布 manifest、二进制 version --json、 兼容矩阵和本页页脚中的版本；任一不一致都应停止安装或升级。

当前版本是内部、单部署租户的现场候选，不是公网、多租户或 Production verified 产品。

第一客户采用 owner_supervised_trial。你不需要理解或保管签名私钥：产品 owner 只确认版本和 现场窗口，Codex 负责从准确 GitHub main/CI 生成、核对、传输、安装和保存 receipt。客户不 能自行升级；第二客户或自助升级前会另行建立正式发布权威。

管理员先阅读“版本与支持边界”“安装与首次启动”“配置、安全与访问”和 “升级、回滚与恢复”。调查操作员可从“执行调查工作流”开始。稳定协议名、 JSON 字段、CLI 参数和 error code 保留英文，以便与实际输出逐字对应。

三条操作原则

  • 不把 fixture/synthetic 结果称作真实生产证明；批准的 sanitized metadata 也不等于 raw 数据。
  • 不从缺失事件推断未观察到的事实；证据不足时显示 gap 或 unknown。
  • 不用递归、通配符或批量删除处理试用数据、备份、receipt 或 evidence。

当前数据进入方式

当前生产意图的数据路径是独立 xinsight-feed.service 通过固定私有 HTTP endpoint 拉取 unirouter.completed-execution.v1。worker 默认不启用；只有写入当前 schema 23、配置私有 endpoint、用 target-local xinsightctl feed-credential 生成并原子激活 feed-only token、 绑定 importer credential，并完成受控 activation 后才可启动。raw token 不离开 X target； UniRouter 只登记严格 public verifier bundle。worker 按 at-least-once 逐项幂等提交，整页 成功后推进 durable cursor，不在 UniRouter 请求热路径上。fixture 与历史 sanitized snapshot sidecar 仍可用于明确的测试/调查，不是 live transport。

第二轮或后续 campaign 不复用第一轮 delivery epoch。schema 22 的 root-only xinsightctl connector-epoch 在 worker inactive+disabled、Cursor=high-watermark 且无错误时， 先生成 SHA-256 绑定计划，再在同一数据库事务中归档旧 checkpoint epoch 并激活新 source instance/Cursor。可变交付状态仍不进入 M0 identity/hash 或 Event-linked provenance； epoch 激活也不会自动启动 Feed。

rc.11 还提供受约束的离线 unirouter import-campaign-package 路径，用于已经预授权、 content-addressed 的 Source-evidence package。它先验证准确的 X 签名发布 manifest、运行中 importer 字节、产品 scope/verification receipt、Neutral N1 授权、purpose-separated Source trust 和不可变 producer package，之后才加载 importer 数据库绑定。该路径没有 endpoint、worker、 Cursor、Checkpoint 或 credential 输入，也不会把带 runtime_close_marker_unavailable 的 partial member 声称为 complete。

rc.12 引入且当前版本保留 xinsight-connector-controller.service：UniRouter 继续调用公开 HTTPS redeem/poll/result API，Web 只在 result durable commit 后通过固定 root:xinsight Unix socket 发送 typed wake。controller 使用独立 admin DSN credential，并在 Web 之前启动；它不接受任意 path、unit、SQL、shell、URL 或 DSN。worker 仍只在 phase-3 active authority 的 fresh readback 后最后启动。

rc.12 引入且当前版本保留第二个独立、缺省 dormant 的 xinsight-litellm-feed.service，从准确私有 HTTPS /spend/logs/v2 读取达到 start-time eligibility fence 的 LiteLLM spend-log metadata；这不声明 row endTime terminal finality。它使用独立六字段非 secret config、 独立的非管理员 team observer API key（团队允许 /spend/logs，key 只允许 /spend/logs/v2）、独立 product registry identity 和独立 durable checkpoint，不修改 completed-execution worker 或 Read API。首次启用、启停、永久错误恢复、key rotation 和 rc.11 rollback 的准确步骤见“配置、安全与访问”；没有 Target/External 证明时 不能把 Local/CI 实现称为已联调或 Production。

当前访问方式

rc.13 新增、当前版本保留 X-Insight 自有的本地账户、内存 Session、RBAC 与最小化审计。所有调查 UI/API 必须先建立产品 Session；investigator 可读 Evidence，operator 还可查看和撤销 Session。 账户只由 root 通过 systemd credential 离线配置，产品不提供 Web 建号、改密码或改角色。

Session cookie 固定为 __Host-xinsight_session，带 Secure、HttpOnly、 SameSite=Strict 和 Path=/，无 Domain；状态变更还要求同源 HTTPS 与 Session-bound CSRF。当前版本支持一个明确 opt-in 的同机 loopback TLS terminator 合同：固定 XINSIGHT_EXTERNAL_ORIGIN，只信任来自 loopback 的准确 forwarded proto/host，并继续让 应用只监听 127.0.0.1:8080。Target 登录仍必须逐次证明证书、Host/Origin、Secure cookie、 匿名 303/401、authenticated readback 与公网只开放 80/443；HTTP SSH tunnel、代理自身登录页 或 loopback HTTP 都不是 Target 登录证明。

当前调查工作台

schema 16–20 的 Case、Finding、Evidence/Gap citation、sealed Evidence Pack、Saved View、 来源声明的 Session、Compare、Feedback、Alert-to-Case、版本维度、Gap resolution 和 Known/Unknown Discovery 都是产品本地调查对象。它们引用 M0 Evidence 的稳定 ID/hash，不会 改写来源事实；Discovery 输出始终是带 evidence refs、limitations 和 abstention 的假设，不会 自动执行策略或关闭 Gap。

当前调查界面按“运行态势—调查—分析—信任与访问”组织。/inbox 的运行态势使用同一组固定 as_of/from/to 聚合 Alert、execution、Gap、四个独立覆盖口径和来源声明的 Runtime Path；不会从 Execution 搜索第一页制造全局趋势，也不复制 MaaS 控制台的运营指标。Alert 按 observed 窗口筛选并 读取当前状态，不声称重建历史状态；未关联 execution 的 Alert 不会借用其他 Trace。Connector 当前 trust/checkpoint 与固定 Evidence 统计分开显示，前者不进入事件 hash。

Execution Story 首屏按“发起者—动作—经过系统—终点”展示来源可证明的路径；没有来源 identity 或 declared parent 时明确显示未知，不会用时间相邻补线。桌面因果图和小屏关系列表表达同一组 edges[]。完整覆盖、语义说明、Saved View 和 Finding 编辑采用渐进披露；记录了 Gap 或完整性未 闭合时仍默认展开。Connector 页面把来源契约、可变交付运行状态和 Checkpoint 摘要分开，后两者 不冒充 Evidence。

产品仓已固定不可变 Foigent Protocol v2.0.2 用于共享 CI 与 source-neutral 合同验证。该 PATCH 使远程 composite Action 可在无 .git、无权威仓历史、 无产品侧私有仓凭据的 snapshot 中运行；Event/Connector Schema、vectors、reports、投影输出 和 M0 identity/hash 相对 v2.0.1 保持不变。现有 UniRouter/LiteLLM worker 仍使用各自已验证 的 v1 runtime binding。 OpenInference 已有 metadata-only bounded-offline 解析/投影、不可变 completed operational receipt 与离线导入命令。rc.5 只增加 exact root-owned expiring non-production authorization： 它绑定 target machine ID、release commit/version、bundle path/SHA、operation、producer、scope 和最多 10 条 record；没有授权会在 bundle、credential、数据库之前 fail closed。它不启用 production bootstrap、入站 OTLP listener、Feed、Cursor 或 Checkpoint。Investigation 新增 Trace Journey 只读投影，在不改变 M0 request/event/hash 的前提下，以 exact source/scope/trace 跨 execution 展示来源声明的父子 Span 路径。

需要保留的证据

每次安装、升级、回滚、恢复和现场调查都应保留：准确 release/commit、manifest 与 artifact SHA-256、bootstrap/trust-store SHA-256、GitHub workflow/CI、签名 key ID、 xinsightctl receipt、兼容性/监听检查、使用的数据 proof class，以及 Local、CI、Target、External integration、Production 各自状态。

  • 不是完全 air-gapped：发布包、信任根和已固定 PostgreSQL image 可经批准的私有路径传入。

    • metadata；不保存 raw prompt/response。

  • 第一客户为 owner_supervised_trial：产品 owner 与 Codex 执行所有安装/升级；一次性签名私钥不交付、不保留，客户不能自助升级。这不是持久商业发行权威。

产品概览与术语

X-Insight 是异步调查与证据解释平面。它从持久化 evidence events 派生 execution、timeline、 selected-node、source/provenance 和 capture-gap 视图；UI node 不是新的事实源，也不会回写 来源事实。

时间与因果

effective_at 用于产品 timeline 的稳定顺序；occurred_at、ingested_at 和来源时间用于 解释采集过程。多个时间不一致时，UI 会标注，而不是改写来源。declared parent 未解析时， 仍保留声明和 gap，不把相邻事件画成已证实因果。

数据最小化

当前产品只面向 metadata。任何 request ID、actor、model、policy、usage、错误和来源引用都 必须先通过批准的 sanitized 规则。metadata_only 描述捕获模式，不保证每个字段都安全； custodian 仍需审查输入。

Known / Unknown 纪律

调查 UI 把声明分为直接观察、来源声明、确定性派生、假设与未知。Capture Gap 是可查询的一等 Evidence 边界；设置 resolution state 只记录调查进展，不删除 Gap，也不把未知变成已知。 Compare 中 Missing、Partial 与数值 0 不可互换。Discovery 证据不足时必须 abstain，不能 为了填满图表生成结论。

产品本地对象与不可变 Evidence

Case、Finding、Annotation、Saved View、service identity、Feedback、Alert link 和 Gap resolution 存在于产品本地 Workspace/分析层。Evidence citation 同时保存稳定 ID、hash/source ref snapshot 与 relation；Finding 可以分别关联 supports、contradicts、context 或 limits 的 Evidence/Gap。sealed Case 固定 revision、digest 与 pack bytes，之后不能静默编辑。

  • X-Insight 应用和 PostgreSQL 不开放公网监听；如需现场公网登录，只允许经批准的同机 HTTPS

第一客户的信任引导

你不需要生成密钥、保管 U 盘或执行签名命令。Codex 在 GitHub 手动发布流程中完成以下工作：

  1. 只接受准确的当前 main commit 和同一 commit 已成功的 CI push run；
  2. 自动生成一次性 Ed25519 key 并构建 signed-v2 release；
  3. 在组装交付目录前删除私钥；
  4. 只交付 artifact、bootstrap verifier、公开 trust store、build result、边界说明、SHA256SUMS 和 owner-supervised-trial-release.json；
  5. 在本地和目标主机分别核对 commit、workflow run 与 SHA-256。

配置、安全与访问

配置与 secret 边界

/etc/x-insight/xinsight.env 只允许 XINSIGHT_MIGRATIONS_DIR=/opt/x-insight/current/migrations。 Reader、Workspace、Importer 和 Admin DSN 分别保存在 /etc/x-insight/database/sets/... 的 root-only 文件中；current 符号链接原子选择当前 credential set。systemd 只通过 LoadCredential 把 reader 与最小权限 workspace DSN 交给服务。Web 服务用 reader 查询 Evidence，用 workspace 写入 Case/Finding/Annotation/Gap resolution 等产品本地调查记录； workspace 角色不能修改 Evidence identity/hash、Connector 交付状态或迁移账本。Web 服务不得 获得 importer/admin DSN、feed key 或 Source key。

One-click Connector target 配置

受管安装会 generate-once 创建 /etc/x-insight/xinsight-connector-id.env，mode 为 0600，并在 install/upgrade/re-upgrade 中校验后原字节保留。该 installer-owned identity 文件只允许一个 key：

XINSIGHT_CONNECTOR_DEPLOYMENT_ID=xid_INSTALLER_GENERATED_22_BASE64URL_CHARS

受支持的 root CLI 只在另一个 root-only /etc/x-insight/xinsight-connector.env 原子写入一个 target key：

XINSIGHT_UNIROUTER_INSTALL_ORIGIN=https://APPROVED_UNIROUTER_ORIGIN

不要创建、复制或编辑 identity 文件。deployment ID 不是 bearer credential，但它是 installation/replay 绑定的稳定部署身份；不得按发布版本、服务重启或 Connector 重试轮换。 deploy/xinsight-connector.env.example 只说明 target 形状，不是待复制到 /etc 的配置。UniRouter origin 必须是规范化 HTTPS origin：无 userinfo、path、query 或 fragment。

完整启用条件分布在三个 root-owned 配置面：

  • /etc/x-insight/xinsight-connector-id.env 只提供 installer 生成的稳定 deployment ID；
  • /etc/x-insight/xinsight-connector.env 只提供 CLI 设置的 UniRouter install origin；
  • /etc/x-insight/trusted-tls-proxy.env 提供准确

    • XINSIGHT_EXTERNAL_ORIGIN=https://APPROVED_XINSIGHT_ORIGIN，并按本章网络边界启用可信同机 TLS terminator。

xinsight.service 依次加载 TLS、identity 与 target 文件。UniRouter install origin 缺失时，即使 stable ID 已生成且已经配置 TLS/external origin，Connector 仍明确 disabled，Web 可正常启动且不会 产生 Connector 流量。一旦 target 文件存在，三项必须同时有效；缺失 ID、缺失 X-Insight external origin 或任一 origin 非规范 HTTPS 都会 fail closed 并阻止服务启动。配置文件本身不会 activate/enable/start Feed worker；worker 仍只能在独立三阶段 authority 的最后一步启动。

受支持的应用顺序如下；先完成并核对本章后述的 trusted TLS 文件，再由准确 current release CLI 验证稳定 ID/owner/mode/key allowlist 与 TLS external origin，最后原子设置 target：

sudo /opt/x-insight/current/bin/xinsightctl connector-target-config validate
sudo /opt/x-insight/current/bin/xinsightctl connector-target-config set \
  --unirouter-origin https://APPROVED_UNIROUTER_ORIGIN
sudo /opt/x-insight/current/bin/xinsightctl connector-target-config validate
sudo systemctl restart xinsight.service

不要用编辑器、sed、重定向或复制模板改写 managed Connector 文件。set 只接受规范 HTTPS origin，只更新 target 文件，无法写入 identity key；写入使用完成 sync 的 staging 与原子 rename， 不会留下半文件覆盖当前 target。每次 Web 启动还会通过 root-only、clean-environment ExecStartPre 再次校验三个文件的 owner/mode/key、deployment ID 形状以及 full target 的 TLS 前件； 任一漂移都会在 Web 进程前失败。上述 restart 是独立现场授权动作；仅写配置仍不启动 worker 或发送 流量。

本地账户、Session 与 RBAC

当前版本的账户 authority 是一个 root-provisioned、只读的 systemd credential： /etc/x-insight/access-accounts.json。xinsight.service 只以 LoadCredential=access-accounts.json:/etc/x-insight/access-accounts.json 读取它；不允许 把账户 JSON、password 或 hash 放进 xinsight.env、其他 environment、argv、仓库、 receipt、日志或工单。

文件必须是 root 或实际 service EUID 所有的 regular、single-link、非 symlink 文件， mode 只能是 0400 或 0600。大小上限 64 KiB、账户上限 100；服务启动时会在 open 前后复核 identity/metadata，并对 duplicate key、unknown field、trailing JSON、重复 subject、 重复规范化 username 或不合规 hash fail closed。没有默认账户；空账户集也会拒绝启动。

严格形状如下；占位 hash 不能直接使用：

{
  "schema_version": "xinsight.local-accounts.v1",
  "accounts": [
    {
      "subject_id": "xs_REPLACE_WITH_32_LOWER_HEX",
      "username": "operator.one",
      "role": "operator",
      "disabled": false,
      "password_hash": "$argon2id$v=19$m=19456,t=2,p=1$REPLACE_WITH_SALT$REPLACE_WITH_HASH"
    }
  ]
}

subject_id 必须匹配 xs_[a-z0-9]{16,64}，且以后不因 username 变化而复用给另一身份。 username 必须是已经 trim/lowercase 的 3..64 字符 ASCII [a-z0-9._-]；角色只允许 investigator|operator|access_operator|platform_admin。每个账户的五个字段都必须显式存在； disabled 必须是 JSON boolean，缺失、null 或字符串都会 fail closed，不能用隐含默认值。 密码 hash 只接受准确 Argon2id v19： memory 19456 KiB、iterations 2、parallelism 1、16-byte salt、32-byte key。

离线 root workflow：

sudo /opt/x-insight/current/bin/xinsightctl access generate-subject
sudo /opt/x-insight/current/bin/xinsightctl access hash-password
sudo /opt/x-insight/current/bin/xinsightctl access validate \
  --file /etc/x-insight/access-accounts.json

hash-password 只在交互 TTY 隐藏读取两次 password；stdin/pipe、flag、environment 和 非交互输入都会拒绝。密码最少 12 bytes、最多 1024 bytes。命令只输出 Argon2id PHC string；该 hash 仍是敏感配置材料，只能在同一目标主机的 root-only 编辑流程中处理，不得进入 shell history、command substitution、共享 clipboard/transcript、截图、日志或聊天。 validate 只输出 schema 与角色/disabled 计数，不输出 username、subject 或 hash。

配置变更只能由另行授权的 root operator 原子写入并复核 owner/mode/regular/nlink 后重启 服务；产品没有 Web 建号、password reset、改角色或写回文件能力。disabled=true 会阻止新 登录，但既有内存 Session 必须通过 restart 或 operator revoke 失效；因此禁用账户的受控 procedure 应同时处理既有 Session。

产品 Session：

  • cookie value 为 256-bit 随机 opaque token，服务端只以 SHA-256 digest 作 key；
  • cookie 固定名 __Host-xinsight_session，Secure、HttpOnly、

    • SameSite=Strict、Path=/、无 Domain；

  • 每次成功登录都轮换 cookie 并撤销请求携带的旧 Session；
  • idle timeout 30 分钟、absolute timeout 8 小时、每 subject 最多 5 个、单进程最多 500 个；
  • Session 只在内存中，进程重启全部失效；logout 与 operator revoke 会立即撤销；
  • 所有认证状态变更要求单一同源 HTTPS Origin、同源 fetch、严格 JSON，以及

    • Session-bound X-CSRF-Token。

登录失败对 unknown username、错误 password 与 disabled account 使用同一响应。默认门禁为 每个规范化 username 在 15 分钟窗口内最多 5 次失败、全进程在 1 分钟窗口内最多 50 次失败； 另有独立的 Argon2id verification admission，默认最多 4 个并发。达到任一边界都在进入新的 password verification 前返回 429 authentication_rate_limited；这与调查 API 的 32 并发 上限相互独立，不能用扩大通用 API 容量替代 password verification 的内存边界。

    • checkpoint 上更换。

Receiver-generated feed credential

feed credential 必须在准确 X-Insight target 上由 root 本地生成。UniRouter 只接收 prepare 输出的 Frozen Registration Bundle V1，不接收 raw token：

sudo /opt/x-insight/current/bin/xinsightctl feed-credential prepare
sudo /opt/x-insight/current/bin/xinsightctl feed-credential status

prepare 的 stdout 是严格六字段 public JSON：schema_version、token_format、 verifier_scheme、key_prefix、verifier_sha256、operation_id。原始 token 是 32-byte crypto/rand 值编码成准确 ur-xf1- + 64 个小写十六进制字符，只写入 /etc/x-insight/unirouter-feed.key.next。该文件必须是 root:root 0600、regular、 single-link、非 symlink；非 secret 可恢复状态位于 /var/lib/x-insight/control/feed-credential-operation.json。

初次激活顺序固定为：X prepare；Uni 在 paused 状态登记 public bundle；X 使用 .next 中的 staged token 对准确私有 endpoint 做认证预检，并且只接受严格 completed_execution_feed.connection_paused、retryable=true 的 503 envelope； 随后才使用 bundle 中的准确 operation/verifier 原子替换并 restart；Uni 再 promote 并 resume：

sudo /opt/x-insight/current/bin/xinsightctl feed-credential activate \
  --operation-id PUBLIC_OPERATION_ID \
  --verifier-sha256 PUBLIC_VERIFIER_SHA256

activate 使用 xinsight-feed.env 中与 worker 相同的固定 endpoint、system-root TLS、 no-proxy/no-redirect 和 bounded timeout 语义，在 process memory 中使用 .next token。 401、403、200、非严格 envelope 或 transport failure 都必须在替换前失败，保留旧 live credential、.next 和 prepared state；systemd unit 已 active 也不能替代该证明。 预检通过后才原子替换 /etc/x-insight/unirouter-feed.key 并执行 systemctl restart xinsight-feed.service；它不把 secret 放进 argv/env，也不 enable unit。 如果进程在 replace/restart/state-finalize 之间中断，用同一 operation/verifier 重跑 activate，不得生成新 token。若 activation barrier 尚未跨越，可准确取消 pending：

sudo /opt/x-insight/current/bin/xinsightctl feed-credential abort \
  --operation-id PUBLIC_OPERATION_ID \
  --verifier-sha256 PUBLIC_VERIFIER_SHA256

rotation 时旧 live credential 必须保持 active；暂停 Uni source 后，用 status 中的准确 active operation/verifier 绑定 replacement prepare：

sudo /opt/x-insight/current/bin/xinsightctl feed-credential prepare \
  --expected-active-operation-id CURRENT_PUBLIC_OPERATION_ID \
  --expected-active-verifier-sha256 CURRENT_PUBLIC_VERIFIER_SHA256

随后仍按“Uni stage paused → X staged-token authenticated paused 503 → atomic activate/restart → Uni promote/revoke old/resume”完成。永久 401 会让 worker fail closed 并保持 durable cursor； 修复 credential 后的 restart 从同一 cursor 重试，不得 reset/backfill 数据库。

不要把 DSN、密码、token 或 raw evidence 写入：

  • release artifact、手册、receipt、install-state 或 operation journal；
  • shell history、命令参数、systemd Environment、截图或工单正文；
  • Git 仓库、共享 cooperation 目录或未经批准的诊断包。

网络与访问

X-Insight 进程和 PostgreSQL 都必须 loopback-only。当前版本的身份验证、Session 与上述 RBAC 仍由 X-Insight 自己执行；TLS terminator 不是身份 authority，也不能注入用户/角色 assertion。

默认不信任任何 forwarded header。只有 root 创建严格 /etc/x-insight/trusted-tls-proxy.env 并重启服务后，才启用同机代理：

XINSIGHT_TRUSTED_TLS_PROXY_MODE=loopback
XINSIGHT_EXTERNAL_ORIGIN=https://APPROVED_HOST_OR_IP

文件只能有这两个非 secret 值，必须 root:root regular、非 symlink、mode 0600。origin 必须 是无 path/query/fragment/userinfo 的规范化 HTTPS origin。后端只接受 loopback remote、唯一 X-Forwarded-Proto: https、唯一且与 origin 相同的 X-Forwarded-Host、准确 Host/Origin、 same-origin fetch 和空通用 Forwarded。Nginx 必须覆盖而不是追加客户端 forwarded headers， 其他 server block/default host 必须拒绝。任一不匹配都按非 TLS fail closed。

Target 还要验证 certificate/key ownership 与自动 renewal、Nginx request bounds、应用/DB listener 仍为 loopback、公共安全组和 UFW 仅 80/443、HTTP 只做 ACME/HTTPS redirect，以及 旧 release rollback。HTTP SSH tunnel、一般私网、代理自身 login page 或 localhost HTTP 都 不等于 X-Insight Secure-cookie Target 证明，也不得通过去掉 Secure 或放宽 same-origin/CSRF 来绕过。

feed endpoint 默认必须是固定 HTTPS URL。只有部署证据能够证明固定 literal address 承载于已认证的 loopback/RFC1918/Tailscale/ULA 私有 tunnel 时，才可把 XINSIGHT_UNIROUTER_FEED_ALLOW_PRIVATE_TUNNEL_HTTP 明确设为 true；一般私网地址本身不 等于已认证 tunnel。worker 禁用环境代理与 redirect，并限制 connect/header/request timeout、response header、page body 与 page count。systemd 默认拒绝公网 egress；实际 endpoint 与 tunnel 属性仍须在受控部署中逐字核对。

数据准入

fixture/synthetic 用于功能证明，不含真实用户事实。internal-real development metadata 是 项目自有非生产环境中真实发生、但不含客户事实的执行元数据；customer sanitized metadata 则是客户批准后保留调查所需最小字段的真实来源元数据。后两类都必须明确字段范围、 custodian、用途、保留时间和退出动作，并使用独立 trial database。三类都不得包含 raw prompt/response。

  • source 与 proof class 可追溯；request/trace/actor/model/policy 标识已按批准规则处理；
  • 自由文本、header、body、tool argument、附件和 secret 已排除；

  • 历史 internal-real/customer sanitized artifact 与其 exact approval manifest 先共同通过

缓存与清理权限

X-Insight 当前没有用户权限缓存控制面。谁可启用、读取、清除身份/权限缓存由 X-IAM 或客户 IAM 的 authority 决定；X-Insight 只记录获准输入的结果/证据。任何未来 cache invalidation contract 必须版本化、可审计，不能让调查 UI 获得实时授权写权限。

升级、迁移、回滚与恢复

升级是 root-only、单节点、受监督维护窗口操作。产品 UI 不持有 systemd、release directory、 credential 或数据库备份权限。

第一客户的升级仍由产品 owner 与 Codex 执行。产品 owner 不操作签名密钥；Codex 先核对准确 GitHub main/CI/workflow 和 delivery SHA-256，再运行下面的 preflight 与升级命令。客户不能 自行选择或安装一个未记录的包。

正常升级

先按“安装与首次启动”的信任引导，用已核对 hash 的 bootstrap 验签并把 next release 解到 尚不存在的 /approved/staging/xinsight-NEXT-COMMIT。跨版本升级必须由这个已验证目标 payload 内的控制器执行，先 preflight：

sudo /approved/staging/xinsight-NEXT-COMMIT/bin/xinsightctl version --json
sudo /approved/staging/xinsight-NEXT-COMMIT/bin/xinsightctl upgrade --check --artifact /approved/path/NEXT-RELEASE.tar.gz
sudo /approved/staging/xinsight-NEXT-COMMIT/bin/xinsightctl upgrade --artifact /approved/path/NEXT-RELEASE.tar.gz

preflight 验证签名/revocation、平台、准确支持的来源版本、当前 release 无漂移、schema/config 兼容、PG16 client、磁盘、备份空间、无其他 writer/session、loopback listener，以及当前 root-only /etc/x-insight/access-accounts.json 的严格 identity/mode/content。credential 必须先用目标 staging 的 xinsightctl access validate 校验；缺失或漂移要在 journal、备份、 迁移和服务变更前 fail closed。升级按顺序持久化 journal、禁用 importer、备份、 expand-first migration、切换 immutable symlink、启动并证明 readiness/代表性读取与匿名 认证门禁，最后写 sanitized receipt。

不得用 /opt/x-insight/current/bin/xinsightctl upgrade 代替目标控制器。旧版本控制器只知道 自身发布时存在的 runtime file inventory，可能在数据库和应用升级成功后漏装 next release 新增的 systemd unit。目标控制器仍会严格验证当前与目标 artifact、支持路径和现有受管状态； 使用目标控制器不是跳过 preflight。

若 feed worker 已存在，upgrade/rollback/restore 会先持久化其 present/active/enabled 状态并 stop/drain，再关闭 importer LOGIN；迁移与产品读取验证通过、importer LOGIN 恢复后， 只按原状态恢复受支持版本的 worker。active 与 enabled 独立保留；例如升级前 active+disabled，升级后仍为 active+disabled。fresh install 只安装 unit，不自动 enable/start。

受管 Connector identity/config 与 release 文件分离：/etc/x-insight/xinsight-connector-id.env 只能 包含合法 stable deployment ID，/etc/x-insight/xinsight-connector.env 只能包含可选的规范 HTTPS UniRouter origin。upgrade --check 会在任何 journal、备份、迁移或服务动作前分别验证已存在的文件； 实际 upgrade 按原字节保留两者，不生成新 ID、不覆盖 target。来自尚无 identity 文件的受支持旧版本时， preflight 接受缺失状态，upgrade 在安装 runtime files 时只生成一次 deployment ID，仍保持 target 未配置、 worker inactive/disabled。生成使用完成 fsync 的 staging、no-clobber 发布与目录 sync；中断恢复只发布 完整文件，不会让空/半写最终路径阻塞 resume。应用回滚不删除 identity/target，随后 re-upgrade 继续复用 同一 ID 和 target。仅配置 TLS external origin 也是独立有效状态，不会被当成部分 Connector 配置。

中断恢复

跨版本 operation 完成前，必须继续使用启动该 operation 的同一个已验证目标控制器；中断点 可能仍在切换 current symlink 之前，不能退回旧 current 控制器：

sudo /approved/staging/xinsight-NEXT-COMMIT/bin/xinsightctl status
sudo /approved/staging/xinsight-NEXT-COMMIT/bin/xinsightctl recover
sudo /approved/staging/xinsight-NEXT-COMMIT/bin/xinsightctl resume

status 显示当前 managed identity 和 active operation；recover 只读判断 durable phase 与 允许动作；resume 从已记录边界幂等继续。operation 成功并且 status 不再有 active journal 后，日常状态与后续当前版本操作才切回 /opt/x-insight/current/bin/xinsightctl。 只有 recover 明确允许且尚未越过不可安全撤销 barrier 时，才可用同一目标控制器执行 abort：

sudo /approved/staging/xinsight-NEXT-COMMIT/bin/xinsightctl abort

不要手工删除 active-operation、改 symlink 或编辑 receipt 来伪造完成。

应用回滚

当数据库 schema 仍处于 prior application manifest 声明的兼容范围、配置兼容、previous release 无漂移且备份仍有效时，先检查再切回准确 previous binary：

sudo /opt/x-insight/current/bin/xinsightctl rollback --check --previous
sudo /opt/x-insight/current/bin/xinsightctl rollback --previous --reason-code field_validation

允许 reason code 为 failed_readiness、field_validation、operator_request。应用回滚不执行 down migration；数据库保持 expand-first 后的 schema。若 prior binary 不声明兼容，应拒绝， 不能强制切换。

0.3.0-rc.13 当前 schema 为 23；既有应用只声明到 schema 20，当前单一 manifest rollback policy 不按每个来源版本放宽。因此 0.3.0-rc.13 manifest 的 application_rollback_compatible 为 false，rollback --check 会 fail closed；需要回到 旧应用时必须使用下面的隔离恢复，不能因迁移看似“只有新增列”而扩大旧 manifest 的 database_schema_min/max。schema 16–23 包含 Workspace、Agent Access、分析扩展、 bounded-offline provenance 约束、immutable completed operational receipt、不可变 checkpoint epoch history、Connector installation 与三阶段 control operation；这些 additive 事实也不能扩大旧应用的 rollback 合同。

隔离数据库恢复

数据库损坏、迁移后的数据状态必须回到备份，或应用回滚不兼容时，恢复到一个新的 xinsight_restore_* 数据库，验证后再原子切换 credential set；不覆盖当前数据库：

sudo /opt/x-insight/current/bin/xinsightctl restore --check --backup /var/backups/x-insight/EXACT.dump --backup-sha256 sha256:EXACT --new-database xinsight_restore_YYYYMMDD
sudo /opt/x-insight/current/bin/xinsightctl restore --backup /var/backups/x-insight/EXACT.dump --backup-sha256 sha256:EXACT --new-database xinsight_restore_YYYYMMDD --reason-code database_recovery

允许 reason code 为 database_recovery、field_validation、operator_request。失败时工具必须 恢复原 credential link；原数据库和 backup 保留，直到 custodian 做明确处置。

PostgreSQL admin credential rotation

database-admin-credential 是 root-only 的管理凭据生命周期，不是账号密码、Connector credential、 DATA_RESET 或数据库恢复工具。它只替换四角色 active database set 的 xinsight_admin 成员； xinsight_reader、xinsight_workspace、xinsight_importer 三个 DSN 必须逐字节继承。执行窗口要求主服务 正在运行且 PID 稳定、两个 Feed worker present/inactive/disabled、其他 xinsight_admin session 为零。 先取得不含 secret 的 preview：

sudo /approved/staging/xinsight-0.3.0-rc.13-COMMIT/bin/xinsightctl database-admin-credential preview \
  --authorization-ref decision://EXACT-AUTHORITY \
  --reason-code local_tooling_exposure

preview 绑定准确 release/commit/schema/config/protocol、active set 和四成员 metadata/canonical digest、 PostgreSQL 16 与 admin role identity、34 表/migration/connector/checkpoint/account/config 指纹，以及精确 worker/PID 状态。它不会输出 DSN、密码或 verifier。批准后把以下严格 JSON 写入 root-owned、single-link、 regular、0400 或 0600 的绝对路径文件；不要把内容改成 argv 参数：

{
  "schema_version": "xinsight.admin-credential-rotation-request.v1",
  "preview_sha256": "sha256:EXACT-PREVIEW",
  "authorization_ref": "decision://EXACT-AUTHORITY",
  "reason_code": "local_tooling_exposure"
}
sudo /approved/staging/xinsight-0.3.0-rc.13-COMMIT/bin/xinsightctl database-admin-credential apply \
  --request-file /root/xinsight-approved/admin-credential-rotation.json

successor 先在 managed sets 同父目录的唯一 0700 staging 中完整写入并同步四个 0600 成员，验证三项 继承原字节、admin identity 不变且 secret 不复用后，才原子 rename 到 journal 的最终目录。最终目录一旦 存在只按不可变完成态验证，绝不原地修补。verifier 变更前可以 xinsightctl abort；变更后只能 xinsightctl resume，不得把 predecessor 重新激活。产品在受控 predecessor transaction 中紧邻更新前 再次确认其他 admin session 为零；更新后原子切换 active set，终止竞态/恢复残留 session，并证明 fresh successor 成功、fresh predecessor 得到预期 authentication rejection。成功后 predecessor set 只保留为 sealed/inactive，删除由另一个 exact-path retention 操作决定；本生命周期不删除任何文件或目录。

会话静默只统计 PostgreSQL backend_type=client backend 的 xinsight_admin，不能把 logical replication launcher 等数据库后台进程算成管理员工作，也不能终止它们。preflight 只做有界只读观察，不会终止已知 并发工作；最终 verifier transaction 会再次原子核对其它 admin client session 为零。若 ALTER ROLE 已提交、 但进程在 journal 写入前失联，后续 abort/resume 必须重新探测 predecessor/successor 认证状态：一旦确认 successor 已成为权威，abort 必须拒绝并把操作持久化为 resume-only，resume 不得重复更新 verifier。

receipt/journal 只有 alias、metadata 和 digest。demo.operator 文件/verifier、产品表、schema ledger、 service identity、Connector credential/config、Cursor/Checkpoint 与 protocol pin 必须不变；主服务不重启， 两个 Feed worker 不启动/enable，poll/traffic 为零。

第二轮联调 fresh-database clean baseline

clean-baseline 不是通用清库工具，只用于联合裁决后的 full-product 第二轮联调基线。执行前必须 先让双方 traffic quiescent，并在 X-Insight 两个 Feed worker 均 present、inactive、disabled 时 生成 schema-current PostgreSQL 16 custom-format backup，记录绝对路径和 SHA-256，并单独通过 PostgreSQL 16 pg_restore --list。rc.7 upgrade 前的 schema-19 backup 或任何未在当前窗口生成的 旧 backup 都不能替代这一步。

DATA_RESET 与 BOOTSTRAP 是两次独立授权、两份 preview 和两份 durable receipt。DATA_RESET 不得 接受 next source/cursor/epoch。先只读预览 fresh DB cutover 与 credential retirement：

在生成 DATA_RESET preview 前，先用当前已验签 binary 读取 release expected contract，并对当前库 做 root-only、只读 introspection：

/opt/x-insight/current/bin/xinsightctl schema-contract expected
sudo /opt/x-insight/current/bin/xinsightctl schema-contract inspect

valid=true 才表示 named semantic contract、schema 23、PostgreSQL 16 与完整 migration-set 收敛。 column_layout_matches=false 只说明物理 ordinal 不同，不参与 authorization；任何 missing_object、unexpected_object、semantic_property_drift 或 release identity mismatch 仍会 给出脱敏对象身份与 digest，并阻止 preview。命令不输出 DDL、行数据或 credential。

sudo /approved/staging/xinsight-0.3.0-rc.13-COMMIT/bin/xinsightctl clean-baseline data-reset-preview \
  --rollback-backup /var/backups/x-insight/EXACT-SCHEMA23.dump \
  --rollback-backup-sha256 sha256:EXACT \
  --new-database xinsight_clean_YYYYMMDD

preview 必须逐项给出 34 个 public table 的 current_rows/protected_rows/rows_to_zero 与稳定 semantic digest，并证明 exact schema/FK/trigger/namespace/function/extension/type contract、一个 release source、两个 release adapter、旧 binding identity 的 raw-free 摘要与历史最大 epoch、账号唯一性， 以及 UniRouter active/staged/operation-state、LiteLLM credential/environment 五个文件的存在性元数据。 LiteLLM environment 属于旧 campaign source/org/project scope。任何 unknown object、catalog drift、 已存在目标数据库、worker 状态变化、backup/hash 漂移、账号不唯一或 credential 文件类型/owner/ mode/link 漂移都停止。准确 DATA_RESET baton 只允许：

sudo /approved/staging/xinsight-0.3.0-rc.13-COMMIT/bin/xinsightctl clean-baseline data-reset-apply \
  --rollback-backup /var/backups/x-insight/EXACT-SCHEMA23.dump \
  --rollback-backup-sha256 sha256:EXACT \
  --new-database xinsight_clean_YYYYMMDD \
  --preview-sha256 sha256:EXACT-PREVIEW \
  --reason-code second_integration_data_reset

DATA_RESET 不把 backup restore 到 live 新库，也不对 live 数据执行 TRUNCATE、CASCADE 或手工 history 删除。它只创建全新数据库并运行当前 release migrations；新库保留 schema ledger、release source/adapter catalog；所有旧 Evidence、Gap、Provenance、 Case、Alert、Analysis、Receipt、Quarantine、Connector state、service identity/token 与 product row 为零，且 adapter_import_states、epoch operation/history 必须严格为 0/0/0。它以 sealed digest 把 fresh rollback backup、旧 binding identity 摘要与历史最大 epoch 写入 receipt，不复制旧 history 到 live DB。文件访问面只保留 demo.operator 的 subject/username/role/disabled/password verifier 原字节，其他账号移除；主服务 PID 必须更换，使旧内存 Session 失效。

在任何 live cutover 前，apply 会在 quiesced 旧库的独占维护边界中把所选 custom-format dump restore 到 operation 唯一命名的临时 xinsight_restore_* 数据库。PostgreSQL major、完整 migration ledger、 静态角色授权、schema contract 与 34 张表的逐行稳定 semantic digest 必须和已授权、停稳后重读的 旧库 preview 完全相同。临时 restore 数据库随后必须删除并证明不存在，backup SHA 与 pg_restore --list 必须再次通过，才能把 sealed isolated-restore proof 写入 durable DATA_RESET receipt。restore、摘要比较、临时库删除或 backup 再验证任一失败都 fail closed；不会生成或激活新 credential set 来完成这次临时验证。

同一 operation 内还会把 UniRouter receiver active/staged/operation-state、LiteLLM credential 与 LiteLLM environment 五个 canonical 文件逐一移入 product-owned quarantine；receipt 前失败恢复精确 原状态，receipt 后逐个移除 quarantine 并证明五个 canonical path 均不存在。流程只读取文件元数据， 不读取或输出 credential/config 内容，也不生成 replacement。若出现 symlink、 多 hard-link、owner/mode/type 漂移或 canonical/quarantine 双写，fail closed。 任何不属于当前 operation 的旧 quarantine 文件也会被视为未清 credential state 并停止。

LiteLLM systemd unit 本身保留且继续 inactive+disabled。当前 Paths 合同没有 OpenInference 等价持久 credential/config 文件，因此 DATA_RESET 不虚构新路径；OpenInference 产品数据由全局 fresh database 归零。只有 DATA_RESET journal completed、严格空库/账号/connector credential/config readback 仍与 durable receipt 相同后， 协调者才可单独签发 BOOTSTRAP baton。checkpoint request 必须使用 xinsight.connector-checkpoint-epoch-prepare.v1，绑定准确 source system、adapter manifest、cursor key、 worker unit、新 source instance、空 bootstrap Cursor/high-watermark 与 authorization reference；文件必须 absolute、root-owned、single-link、regular、0400/0600，raw Cursor 不进入 argv、日志或共享证据：

sudo /approved/staging/xinsight-0.3.0-rc.13-COMMIT/bin/xinsightctl clean-baseline checkpoint-bootstrap-preview \
  --data-reset-operation-id EXACT-DATA-RESET-OPERATION \
  --data-reset-receipt-sha256 sha256:EXACT-DATA-RESET-RECEIPT \
  --checkpoint-request-file /root/xinsight-approved/second-integration-checkpoint.json

sudo /approved/staging/xinsight-0.3.0-rc.13-COMMIT/bin/xinsightctl clean-baseline checkpoint-bootstrap-apply \
  --data-reset-operation-id EXACT-DATA-RESET-OPERATION \
  --data-reset-receipt-sha256 sha256:EXACT-DATA-RESET-RECEIPT \
  --checkpoint-request-file /root/xinsight-approved/second-integration-checkpoint.json \
  --preview-sha256 sha256:EXACT-BOOTSTRAP-PREVIEW \
  --reason-code second_integration_checkpoint_bootstrap

BOOTSTRAP preview 输出 canonical checkpoint request SHA-256；该 digest 同时绑定 authorization reference 与完整 request 内容，apply 中 staged root-only request 必须逐字节得到同一 digest。

BOOTSTRAP 从 sealed historical maximum 严格推导 max+1，拒绝 receipt 中出现过的 source/cursor identity，并只写入一个 inactive/idle、零 counter、无 epoch operation/history 的 state。它要求两个 worker 继续 inactive+disabled，五个 connector credential/config path 继续为空，不启动/enable/poll， 也不生成 credential/config。该 UniRouter-only BOOTSTRAP 不生成 LiteLLM replacement；新 receiver credential 仍由后续独立 credential prepare/register/activate authority 控制。

receipt 前任何失败会删除 operation 的临时 restore 数据库，并恢复旧 database-set link、完整旧账号 文件、importer login 和主服务；新严格空库不删除，保留供取证且不得复用。此时旧库仍只是本次 cutover 的临时 rollback source。durable receipt 已写入后只允许 exact readback resume：再次证明 live link 只指向严格空库、retained dump 的 path/SHA/PG16 archive 与 sealed restore proof 未漂移， 并确认旧库没有 session 后精确 DROP DATABASE 旧库，再证明旧库与临时 restore 库都不存在且 dump 仍通过验证。缺少 dump 或 restore proof 时，必须在旧库删除前停止。之后才移除含其他账号的单文件 前驱备份与 connector quarantine；不允许 abort 已跨过 receipt 的 cutover。

成功 completed 后，目标只保留这一个已验证 custom-format dump 作为 pre-reset rollback artifact； 不会同时保留 predecessor 数据库或隔离 restore 数据库。该流程不会创建/旋转任何 connector credential/config，不启动/enable worker，也不请求或生成 Feed/test traffic；这些必须由后续 BOOTSTRAP/TRAFFIC baton 分别授权。

执行调查工作流

登录与 Session

只从已批准的单一内部 HTTPS origin 打开 X-Insight。登录表单只接受管理员离线分配的 username/password；浏览器和服务端审计都不应显示密码、hash、Session cookie 或 CSRF token。 登录成功会建立新的产品 Session，并使同一浏览器提交的旧 Session 失效。

Session 的 idle timeout 为 30 分钟、absolute timeout 为 8 小时；服务进程重启会使全部 Session 失效。结束调查时使用产品内“退出登录”，不要只关闭标签页。investigator 只能访问 Evidence；operator 可在“会话管理”查看最小化 Session metadata，并按非 secret session_ref 撤销 Session。该页面不是账户、密码、角色、数据库或 worker 管理界面。

登录页若运行在 HTTP、跨 origin、证书/hostname 未验证的入口，必须停止；不要关闭浏览器 cookie 安全属性，也不要把 SSH HTTP tunnel 或代理登录页当作 X-Insight 产品登录。

导航与页面层级

桌面左侧导航按“运行态势”“调查”“分析”“信任与访问”“帮助”分组。中文名称描述用户任务， 次级英文名称对应稳定产品路由。窄屏使用页首“菜单”按钮打开抽屉；选择页面后抽屉自动关闭。 不要把当前登录角色、仅元数据 · 不展示原文 或“来源/导入/投影/因果”边界当成可关闭的装饰。

“运行态势”不是 MaaS 指标副本。先固定时间与来源范围，再从开放 Alert、Evidence Gap、四个独立 覆盖口径和来源声明的 Runtime Path 下钻。execution/Gap/coverage 使用固定 Evidence 快照； Connector trust/checkpoint 和 Case/Saved View 是当前工作区状态。Alert 的 observed 时间受窗口约束， 但当前 state 不等于历史状态重建。没有关联 execution 时应进入 Discovery 或关联 Case，不得用另一 条 execution 的 Trace 补位。

  --max-request-ids 20 \
  --max-events 200

只有 status=pass 才能进入后续导入。预检会读取并计算真实 approval manifest 的 SHA-256， 核对 snapshot v2 中声明的 hash、source instance、批准 request/scenario、批次上限、每个 request 的 org-bound source row、单一 org、counts、artifact hash、source ref 与 payload policy，并对 明显的 email、phone、IP、URL、credential 和未批准自由文本输出不含 metadata key 或 artifact 字段原值的固定 finding path/code。JSON report 不保存输入路径；文件系统失败的 stderr 可能 包含 operator 提供的精确路径，只能留在私有执行日志。它是额外的 fail-closed 护栏，不等于 通用 DLP，也不能替代精确数据授权和私下逐字段复核。source_event_hash 仅检查为 producer-declared 64-hex；X-Insight 不把它表述成本地重算结果。

sudo env XINSIGHT_IMPORTER_POSTGRES_DSN_FILE=/etc/x-insight/database/current/postgres-importer.dsn \
  /opt/x-insight/current/bin/xinsight-importer unirouter gate-a-check \
  --snapshot /approved/path/sanitized-snapshot.json \
  --approval-manifest /approved/path/approval-manifest.json \
  --schema /opt/x-insight/current/schemas/m0/evidence-event.schema.json \
  --receipt-schema /opt/x-insight/current/schemas/integration/import-receipt.schema.json \
  --persist \
  --receipt-output /approved/path/import-receipt.json

输入与 receipt 路径必须是逐一批准的明确路径。重复导入相同 snapshot 应保持幂等；失败或 quarantine 不能被描述成已持久化成功。--receipt-output 只属于 gate-a-check；该路径必须 尚不存在，工具拒绝覆盖既有 receipt。

sanitized batch 的 gate-a-check 必须携带同一 manifest。工具会在同一进程先完成预检，再将 实际 import bytes 的 SHA-256 与预检 hash 比较；两次读取间发生任何 byte 变化都会在持久化前 停止。省略 manifest 的既有兼容路径不能用于本流程，也不能产生 internal-real 验证结论。 只有本次实际 manifest preflight 通过，持久化 provenance 才能标为 operator_approved；snapshot 自报非空 hash/exchange ID 不足以提升证明等级。

搜索 execution

在 /executions 使用 request ID、request ID prefix、source、outcome、has gaps 和时间范围。 默认窗口为服务端 as_of 向前 24 小时，最大跨度 31 天，每页最多 100。搜索结果显示 proof class、freshness、事件数和 gap 数；它们是固定 as_of 下的视图。

Saved View 创建位于折叠的次级动作中，只保存筛选与呈现方式。结果在紧凑桌面或移动宽度会从表格 改为带字段标签的卡片，但 source、outcome、Evidence 状态、payload 和 Gap 语义不变；无需横向 拖动页面才能读取完整记录。0 无已记录缺口 是当前快照的中性陈述，不是来源完整性保证。

如果没有结果：先核对时间范围、source 和 proof class，再核对 import receipt 与 readiness。 不要假设“无结果”表示 UniRouter 没有执行。

阅读 Story、DAG 与 Chronology

先读 outcome-first Story：谁/哪个系统发起、做了什么、来源明确声明经过哪些节点、在哪里结束， 以及哪些结论受 Gap 限制。再检查 causal DAG；边只能来自 API edges[] 与来源 parent 声明， unresolved parent/orphan 必须可见。Chronology 只回答时间顺序，不把相邻 node 画成因果。

Story 中“发起者—动作—经过系统—终点”四步摘要只使用 Evidence identity、request identity 和 来源声明父子边。如果发起者、完整路径或终态关系未声明，对应步骤显示未知/未解析；不要把该提示 解释为系统故障。桌面 DAG 使用完整内容宽度，小屏使用等价的顺序关系列表，不会为了塞入 SVG 而缩小到不可读。两种呈现都选择同一个 Evidence node，并驱动同一详情面板。

若来源提供同一 exact source/org/project/trace 的多个 Span，Trace Journey 会跨 M0 execution 显示来源声明路径。每个节点仍保留自己的 execution/event/hash；点击跨 execution 节点会进入它 自己的 fixed as_of Evidence。只有唯一可解析 parent_span_id 才连边；同 trace、时间接近或 相同模型都不足以证明因果；未解析节点之间显示断点而不是箭头，来源声明形成 cycle 时完整性 失败。source_timeline_complete=false 表示 bounded export 外仍可能有未知 Span，即使可见 parent 全部解析也不能写成完整业务链路。

四个 completeness 轴分别是 Source、Import、Projection、Causal。任一为 partial/unknown 时， 不能用其他轴的 current 状态替代。freshness、Cursor、high-watermark、retry 与 ingestion time 属于运行状态，不进入 M0 hash 或 event-linked provenance。

四轴完整且没有记录 Gap 时，“证据覆盖与完整性”默认折叠，只显示阶段计数和四轴结论；存在 Gap 或任一轴未闭合时默认展开。折叠不删除证据，也不扩大完整性声明。

打开 detail 与 timeline

选择 execution 后先看摘要：request/source/outcome、事件/gap 数、payload capture mode 和 freshness。timeline 按 effective_at 稳定排序；时间异常与 unresolved declared parent 单独标记。 相邻 node 不是自动因果。

分页继续使用服务端返回的 opaque cursor 和同一个 as_of。cursor 过期时回到搜索重新建立 快照，不拼接或修改 cursor。

检查 selected node

选择一个 timeline node，依次核对：

  1. event type、stage、severity 和多个时间；
  2. correlation、identity、capability、decision、usage、outcome、payload policy；
  3. 每个 field group 的 provenance 标签；
  4. source system/version、schema、source event/ref 和 hashes；
  5. declared parent 是否 resolved，以及是否存在对应 capture gap。

UI 不显示 raw source excerpt。出现需要查看 raw 内容的场景，应退出当前产品范围并走客户批准 流程，不能临时扩大采集。

Case 引用卡片默认显示缩短的技术引用；展开后才能查看并复制完整 event hash。缩短只改变视觉 层级，不改变 seal 输入、citation snapshot 或 Evidence identity。

写结论

调查记录至少写 execution ID、固定 as_of、source/proof class、关键 event IDs、provenance、 gap/freshness、观察事实和未知项。结论用“证据显示”“来源声明”“X-Insight 派生”“当前未知” 区分，不把未解析 parent 或缺失 node 写成已证实串谋、故障原因或策略绕过。

Case、Finding 与 Evidence Pack

把需要共同解释的 execution 加入 Case，再创建 Finding。每个 Finding 明确选择 evidence_backed、deterministic_derived、hypothesis 或 unknown，并逐条关联支持、反驳、 上下文 Evidence 和限制/阻断 Gap。Case-level 引用与 Finding-level 引用不同，不应混用。

封存前核对 title/statement、relation、Evidence ID/hash snapshot、Gap affected claim、Annotation 和 Alert link。seal 后生成固定 revision/digest；JSON 与 print-first HTML 应按相同 snapshot 导出。用户输入会原样进入 pack，禁止粘贴 raw prompt、credential 或未经批准的来源内容。

“添加 Finding”默认折叠，避免编辑控件与已保存结论竞争。展开编辑器仍必须选择声明分类；产品 不会把手工陈述静默提升为 evidence_backed 或 deterministic_derived。

Session、Compare 与 Saved View

只有来源提供稳定 Session/Thread identity 时才展示 Session；时间接近不创建会话。Compare 必须 使用同一固定 as_of，版本/用量/时延/完整性字段中的 Missing、Partial 与 0 分开解释。 Saved View 只保存有界 filters 与 presentation，不保存结果快照；重新打开时仍要核对新的 as_of 与 freshness。

Connector 信任与交付状态

Connector 页面分三层读取：来源契约（source、Manifest、Fidelity、payload、idempotency）、 交付运行状态（worker、import、page/commit/duplicate-noop）和 Checkpoint 摘要（只显示 digest/ 是否存在，不暴露可变 cursor）。来源契约可兼容不代表 worker 正在运行；worker degraded 也不 改写历史 M0 Evidence。Cursor、high-watermark、page time、retry 与 ingestion time 只属于 checkpoint/status 或非事件关联回执。

Discovery 假设

Coverage、process、topic、anomaly、coalition 与 authority-drift 输出只用于发现调查方向。先看 method version、sample/minimum、support score、Evidence/execution refs、limitations；样本不足时 必须显示 abstention。调查员可以把候选写入 Finding，但必须保留其假设分类，不能自动关闭 Gap、 改变路由或触发 enforcement。

Source inspection

Source 面板用于核对 source_system_id、source type/display name/version、adapter manifest ID、 schema version、source event identity/ref、event hash、source event hash 和 fidelity。预留的 source type/schema 字段只是兼容性信息，不证明存在可运行 adapter。

hash 证明保存字节或规范化事件的一致性，不证明发布者真实性、语义完整性或因果关系；发布 artifact 的真实性由独立 Ed25519 trust/signature 链负责。

Capture gap

Gap 面板区分 confirmed gap 与 candidate gap，并显示 scope、source ref、时间和可用原因。 常见类型包括 permission_denied、not_available_from_source、not_instrumented、 sampled_out、retention_expired。candidate 只能作为排查方向，不能升级成确认事实。

freshness.sync_state=gap 或 timeline_complete=false 表示当前 timeline 不能作为完整过程。此时 可报告已观察事实，但必须同时报告缺口和未知，不得补画“最可能”的 node。

Proof class

synthetic_fixture 只证明产品路径和预期 UI/API 行为。批准 sanitized metadata 可证明特定现场 输入经过受控路径被保存和读取，但不自动成为 External integration 或 Production verified。 状态提升必须有准确 target、contract、artifact 和独立记录。

Agent 使用单一 Authorization: Bearer xib_...，不能同时携带浏览器 Session cookie。它只允许 GET /api/v1/executions... 与 GET /api/v1/sources，不能访问 Workspace 写路径、Session 管理、service identity 管理、Discovery refresh 或运行时控制。expired/revoked/invalid token 分别 fail closed，单 identity 另有每秒 5、burst 10 的有界速率门禁。

登录 request body 上限 4 KiB，只接受准确 username、password 两字段且拒绝 duplicate/ unknown/trailing JSON。失败响应不区分未知 username、错误 password、disabled account 或 不合规账户状态。默认失败门禁为同一规范化 username 15 分钟内 5 次、全进程 1 分钟内 50 次；独立 Argon2id verification admission 最大并发 4。达到任一门禁返回 429 authentication_rate_limited 与 bounded Retry-After，不会启动新的 Argon2 verification。它与下述通用 API 并发上限 32 是两个独立资源边界。

Session cookie 固定为 __Host-xinsight_session; Secure; HttpOnly; SameSite=Strict; Path=/ 且无 Domain。Session idle/absolute timeout 分别为 30 分钟/8 小时；每个 subject 最多 5 个， 单进程最多 500 个，重启全部失效。登录、logout 和 revoke 的 origin/CSRF 失败分别使用 same_origin_required 或 csrf_validation_failed，不能通过 HTTP、代理登录页或移除 Secure 降级绕过。

Receipt 与历史

安装状态、operation journal、receipts、backups 和 immutable releases 位于 manifest/工具定义的 固定 host paths。只通过 xinsightctl 状态和恢复动作处理，不能编辑 JSON 把 failed 改成 completed。历史 receipt 是 append-only 证据；新的修复或清理写新记录。

升级前后最低核对

升级前保存 current identity、preflight、access credential 只读 validation、evidence fingerprint、backup path/hash。升级后保存 receipt、readyz 的 representative_read: "ok"、listener、匿名 UI no-store 303 /login、匿名 API 严格六字段 401 authentication_required 和 fingerprint。rc.14 还要核对准确 external origin、loopback 代理来源、证书剩余有效期与自动续期、HSTS、Secure cookie、authenticated search/detail/Investigation/Chronology/Proof，以及公网只开放 80/443。不能退化成 HTTP 登录 来补证。application rollback 或 restore 后按目标版本的历史访问合同重新核对：rc.13/rc.14 要求匿名 303/401；rc.12 及更早版本仍使用其历史匿名代表性读取证明，二者不得混用。
