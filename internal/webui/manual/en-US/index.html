X-Insight product manual

This manual describes the complete development candidate, including access, source collection, investigations, costs, runtime evidence, and review. Apache-2.0 licensing does not remove authentication, source consent, field permissions, signatures, or audit requirements. There is no separate paid feature edition.

X-Insight (XI) can be used independently for supported imports, reported work activity, investigation, and review. UniRouter (UR) independently executes and routes authorized model requests, applies execution policy, and records usage and economic facts. When connected, XI receives authorized UR facts asynchronously for analysis and review; it does not enter the synchronous request path. The shared protocols and Integration Control support that connection rather than introduce more products to select.

Build and try locally

Use Go 1.25.12, Node 22.23.1, npm 10.9.8, Python 3, and PostgreSQL 16. From the repository root:

go mod download
npm --prefix frontend ci
node scripts/build-manual.mjs --profile=development-d
npm --prefix frontend run build
python3 scripts/collect-third-party-notices.py --check
go build ./cmd/...
TZ=UTC npm --prefix frontend test

The repository's docs/community/getting-started.md gives the disposable PostgreSQL and real HTTPS browser-harness procedure. That harness creates synthetic data and a test account; it is not an installed service or a real source connection. The normal frontend browser suite uses mocked responses. Keep those evidence levels distinct. Never point integration tests at a valuable database. Do not put a real DSN in a command, screenshot, issue, or shell history.

A clean checkout can prepare an unsigned Linux payload using preinstalled dependencies:

bash scripts/build-signed-release.sh /absolute/new-preflight --profile=development-d --dry-run
bash scripts/build-signed-release.sh /absolute/new-prepared --profile=development-d --prepare-only

Dry-run is read-only identity/toolchain preflight. Preparation builds binaries and payload checksums but does not sign or produce an installable release. Neither operation is a deployment. The source, embedded UI, both manuals, release config, compatibility matrix, and third-party license texts must match the same commit. The preparation result records that commit and each payload digest.

Install and establish access

Managed installation needs an explicitly selected, qualified host, a dedicated empty PostgreSQL16 database, separate admin/reader/workspace/importer roles, an approved service account, and a trusted signed artifact. There is no public stable installer or default production login. Obtain the artifact, bootstrap verifier, and public trust store through the operator's approved release process. A trust store bundled with an untrusted download does not establish trust by itself.

After independently checking the bootstrap verifier and trust authority, verify and extract into a new directory:

xinsight-release verify --artifact /approved/candidate.tar.gz --trust-store /etc/x-insight/trusted-release-keys.json --expected-commit EXACT_COMMIT --expected-version 0.2.0-dev.fpv22
xinsight-release extract --artifact /approved/candidate.tar.gz --trust-store /etc/x-insight/trusted-release-keys.json --destination /approved/staging/candidate --expected-commit EXACT_COMMIT --expected-version 0.2.0-dev.fpv22
sudo /approved/staging/candidate/bin/xinsightctl version --json

Use the verified payload's deploy templates. Preserve the four independent protected DSN files under /etc/x-insight/database/current/: postgres-admin.dsn, postgres-reader.dsn, postgres-workspace.dsn, and postgres-importer.dsn. They refer to one dedicated loopback database and distinct roles; do not pass their secrets as arguments or service environment values. Host tools, file ownership, database identity, listener scope, and profile must pass the controller's checks.

A fresh install needs no account file or default password. After installation, use the private first-owner activation handoff described in [Accounts and project reading](#accounts). An upgrade imports the validated existing v1/v2/v3 account file exactly once; after that the database is authoritative. Daily invitations, recovery and disable/enable are completed on the Accounts page.

sudo /approved/staging/candidate/bin/xinsightctl install --check --artifact /approved/candidate.tar.gz
sudo /approved/staging/candidate/bin/xinsightctl install --artifact /approved/candidate.tar.gz
sudo /opt/x-insight/current/bin/xinsightctl status

Only run the mutating install after its preflight passes and the deployment is authorized. Installation creates the managed deployment identity; do not copy or edit it. A first install does not automatically connect to UniRouter or start an unconfigured source worker. Keep application/database listeners on loopback and configure the approved HTTPS origin and trusted local TLS terminator before browser login. Unauthenticated product navigation redirects to login; unauthenticated API calls return401. Session cookies remain Secure/HttpOnly/SameSite. The browser refuses password submission over plain HTTP.

Connect the first source

An administrator starts setup from Connections. Confirm the exact XI deployment, UniRouter installation, source projects, collection capabilities, and retention choices. Follow the invitation to UniRouter and complete consent there. Historical consent does not override current source policy. Invitation secrets are transient; do not paste them into tickets or persistent browser storage.

The setup page distinguishes waiting for consent, preparing the connection, waiting for data, and actionable failures. Configuration saved is not the same as a worker loading it; a loaded worker is not proof that data arrived. Confirm source status and a received execution with matching source identity. X-Insight receives facts asynchronously; it is not a synchronous admission dependency for UniRouter requests.

With no existing XI retention policy, setup proposes full body,90days,5GiB per project,32MiB per item. This is a draft requiring explicit confirmation. Existing active or disabled policy is reused. UniRouter source capture is independently approved; its normal proposal is full body,30days,5GiB per project,32MiB per item, subject to actual supported protocols and observation points. Metadata collection does not implicitly authorize body capture or reading. Enterprise source-policy changes require the corresponding administrator permissions; project/user exceptions remain effective.

For interrupted setup, return to the same request and inspect its current state before retrying. The UI keeps non-secret request references for the current subject. An expired invitation needs a new review and consent. Do not create a replacement source to hide a failed original connection. Control identity expiry and current-token expiry are checked separately; an active status can still be elapsed. Rotation renews the same identity and its replacement token for a finite24hours. UniRouter automatic communication can rotate a live token within its last6hours; manual mode does not rotate automatically. XI Auto controls its own collectors and does not enable UniRouter automatic communication or restore credentials. Expired control authority blocks activation and project updates; other independent, still-authorized channels may continue.

Recovery after expiry requires current administrators on both sides and the original retained source secret. Revoked access or scope drift is not silently restored. A202 recovery response means pending. In UniRouter manual mode, explicitly continue that same pending operation with its connection Sync once; this does not enable Auto. Verify the same identity, new current-token expiry and confirmed state, then actual activation, project updates and data. An empty run or accepted submission is not recovery success. Control recovery is unrelated to the reader password and does not require resetting that account.

Grant ordinary users the right scope

Owner project-metadata access is also explicit. Use Accounts to preview and confirm the exact account, source, project and fields. Management does not imply data or body access; see [Accounts and project reading](#accounts).

Role capabilities and active grants both apply. Grants form a union; a narrow grant cannot restrict another broad one. UniRouter projects use project-<project_id>, not a bare number. The following is a shape example, not an instruction to grant every project. Replace every identity and scope with an approved, registered value:

{
  "schema_version": "xinsight.workbench-grant-change.v1",
  "action": "create",
  "grant_id": "11111111-1111-4111-8111-111111111111",
  "subject_id": "xs_1111111111111111",
  "source_system_id": "22222222-2222-4222-8222-222222222222",
  "source_project_ref": "project-42",
  "cost_project_ref": "replace-with-actual-cost-project-ref",
  "expected_revision": 0,
  "capabilities": ["summary", "details"]
}
sudo xinsightctl workbench-access apply --file /approved/grant.json --check
sudo xinsightctl workbench-access apply --file /approved/grant.json
sudo xinsightctl workbench-access show --grant-id 11111111-1111-4111-8111-111111111111

Use protected admin access for these commands. Check is read-only; apply rechecks current state and records the change atomically with its audit. Existing grants need their current revision and a complete replace, or explicit revoke; do not replay stale create requests. Budget-only access uses budget_definition, budget_summary, and budget_alert, exact source project, and cost_project_ref:"*". Keep that grant separate from restricted cost details. It does not grant all execution details.

Execution-linked resource reviews also require the exact target and resource-reporter scopes and the relevant source_context, source_identity, and source_cost fields. Preview and submission enforce the same current permissions. C content grants additionally carry explicit content purposes; a v1 example must not overwrite a v2 content grant. Permission changes invalidate old readings. Obtain a fresh reading instead of repeatedly submitting a stale page.

Investigate, read costs, and review

Start with the overview or one of the usage/purpose, runtime/execution, security/review, cost/usage, or source/coverage topics. Select the period and permitted projects, then open the execution. Check its source, execution identifier, reading ID, cutoff, coverage, and evidence references before drawing a conclusion. The same reading freezes the evidence basis; later source revisions do not rewrite it.

Follow an execution to its runtime requests, resources, source facts, and related work. Runtime outcomes and economic facts are separate: a failed or missing charge does not prove an execution failed, and a missing resource event does not prove no access occurred. A provider request shows what was submitted, not what a model internally used. Related work is grouped only when its actual relationship evidence permits it.

Costs retain their original currency and precision. Do not add unlike currencies, source totals and overlapping XI details, or independent snapshots. Budget remaining-to-plan is not a cash balance, reservation, or permission to call a model. Source budget periods retain their UTC bounds; a global seven-day filter cannot redefine a source billing period.

Trend lines connect adjacent valid known points, including an observed zero with incomplete coverage. Missing, invalid, or nonadjacent intervals break the line. An observed zero is not proof of no activity. Positive and negative costs remain visible; negative values may represent corrections. Focus or hover a point for its exact interval and value. Timezone and ISO evidence timestamps do not change when the UI language changes.

For a review, inspect the selected evidence and preview the precise links before saving. A reader cannot gain write permission by receiving broader data grants. Permission loss, expiry, invalid input, and service failure remain distinct states. After saving, open the stored review and return to the original reading. Check both the saved references and the current access result; do not infer success from a click or a stale panel. Subject drafts, filters, and review references remain in place when switching languages; raw source text, identifiers, protocols, and API codes are not translated.

Content, retention, and gaps

Body capture and body reading are separate opt-ins. Read a body only with current content authorization, the exact purpose/reference, and an unexpired copy. Retention or permission expiry can leave permitted metadata visible while removing body access. Unknown, unavailable, unauthorized, unsupported, and expired do not mean empty or zero. Do not reconstruct missing content from an old screen.

The managed body key must be loaded by both the API and relevant worker. A file on disk alone does not establish this. If ciphertext exists and its original key is missing, stop and restore that key; generating a replacement cannot decrypt historical bodies. A complete private backup includes the database and original key. Protect that backup as sensitive data.

Upgrade, recovery, and diagnosis

Verify the exact next artifact and extract its controller before an upgrade. Use the target controller to validate the actual predecessor; do not drive a cross-version upgrade with the old installed controller.

sudo /approved/staging/candidate/bin/xinsightctl upgrade --check --artifact /approved/candidate.tar.gz
sudo /approved/staging/candidate/bin/xinsightctl upgrade --artifact /approved/candidate.tar.gz
sudo /approved/staging/candidate/bin/xinsightctl status

Preflight must leave service state, database, current release, and operation records unchanged. The mutating upgrade needs an approved window, exact source identity, validated backup, and sufficient disk capacity. Preserve the original installation, source identities, grants, checkpoints, retained keys, and facts. A same-schema upgrade still needs artifact and service lifecycle qualification.

xinsightctl backup --output /absolute/private-backup.tar --check
xinsightctl backup --output /absolute/private-backup.tar
xinsightctl restore --recovery-bundle /absolute/private-backup.tar --recovery-bundle-sha256 sha256:EXACT_DIGEST --new-database xinsight_restore_approved --check

Do not run a restore over valuable data. Review the exact private backup digest and a new dedicated database/installation destination, then use the corresponding approved restore procedure. Restoring to a different deployment revokes restored runtime identities and tokens; retained history remains, and reconnection requires current authorization. Expired bodies remain unreadable. A database-only historical backup does not establish restoration of body keys.

After an interrupted operation, keep its identity and inspect status before using xinsightctl recover or xinsightctl resume with that operation's required arguments. These are recovery actions, not generic retry buttons. Diagnose signature/version mismatch, credential ownership, database identity/schema, missing key, denied scope, source expiry, and network errors separately. Never relax checks to bypass one of them.

For a bug report, give the exact commit/profile, OS/toolchain, sanitized reproduction, expected/actual behavior, and whether the evidence is Local, CI, Artifact, Target, or Production. Keep real prompts, bodies, DSNs, tokens, account hashes, private host identifiers, and raw logs out of public issues. Private vulnerability reporting is not yet verified as an enabled repository feature; request a private contact without publishing exploit details. See root SECURITY.md and CONTRIBUTING.md for the current contribution process and manual DCO sign-off.

Accounts and project reading

This chapter describes the FPV22/schema47 source candidate. A local pass does not establish an installed release or Target acceptance.

First owner and existing installations

The native installer initializes the database account authority once. On upgrade, a valid existing v1/v2/v3 local-account file is imported atomically: stable subjects, usernames, roles, disabled flags, and password hashes are retained. Preserve that private original for historical recovery. After initialization the running product uses the database exclusively; editing or restoring an old account file does not reset a password or change a live identity. Database unavailability fails closed.

A new installation without imported accounts has no default password. After installation and approved HTTPS configuration, an authorized host administrator uses the verified controller to create the first owner's private activation handoff. First create a private0700 directory at the chosen path. The output must be a new file in that directory.

sudo /opt/x-insight/current/bin/xinsightctl access bootstrap-owner --username owner --output /approved/private/owner-activation.html --check
sudo /opt/x-insight/current/bin/xinsightctl access bootstrap-owner --username owner --output /approved/private/owner-activation.html

Check is read-only and creates no link or account. The real operation writes an owner-only0600 HTML handoff at the chosen path; its link points only to the installation's configured HTTPS origin. Deliver it securely to the holder. The holder opens the link, chooses and confirms a password of at least12 characters, then signs in normally. Links expire after15 minutes and can be used once. The browser removes the bearer from its URL and does not store it in browser storage. Do not paste the link into chat, issues, logs or shared documents. Keep the output private even after expiry. A handoff-file or commit failure requires inspection of the exact account and retained file before another attempt.

An existing administrator identity prevents creating another first owner. If normal owner access is unavailable, the authorized host administrator can inspect access directory, then use access recover-account --subject EXACT_SUBJECT --expected-revision CURRENT_REVISION --output /approved/private/new-handoff.html --check and the same exact command without --check. This is an explicit emergency path. It preserves the subject and grants, rejects disabled accounts, and does not require the administrator to know the holder's password. Do not edit database tables or the legacy account file.

Normal account operations

Sign in as owner and open Accounts (/access/accounts). Invite a new account is for a username that does not exist. Review the invitation, then confirm the named target and action using your current password in that confirmation. To recover an existing reader, choose Create recovery link on that exact row under Existing accounts, review the named account, then confirm. This is separate from inviting a new account and from confirming a project-reading grant. Share the single-use activation/recovery link only with that holder; the holder sets their own password. Recovery immediately blocks the target's old password and sessions. Password completion and disable/enable advance only that account's authentication revision. Other people stay signed in; no service restart is required. Enabling a pending account still requires its activation. Normal account management cannot disable, demote or recover an owner. Usernames and stable subjects are not renamed here.

After the action succeeds, its result identifies the target and shows its activation or recovery link. Awaiting password setup means the link has been issued, not that the holder has completed it. The holder opens the complete link once, sets and confirms their own password, and sees which account was updated. Setting a password does not sign in as that account. If the browser still has another account signed in, use the explicit sign-out-and-sign-in action; the normal login form is prefilled with the verified target username. The signed-in page displays the actual server-verified account and role.

If a change succeeded but the list could not be refreshed, keep the result and refresh the state without repeating the change. If submission outcome is unknown, the page blocks another write until its state is checked. A password submission with an unknown outcome does not reuse the one-use link; check the current session or try normal sign-in. Do not infer failure merely from a missing confirmation or repeatedly generate links.

The normal entry follows current reading capabilities: a metadata-only account opens Runtime without probing economic summaries or resource activity it cannot read. A local denied panel does not log the account out. Expiry, revocation, or a changed account still closes protected data and requires a current session. Body-unavailable feedback does not establish that a body was captured or that this account has permission to read one.

Owner reading is explicit

Management capability does not grant access to source data. In Project reading, select the intended account, registered source, exact project and allowed metadata fields. Preview the exact change, check the account/project/fields, then confirm with your current password. The page never copies another reader's grant. It cannot create wildcard, content, purpose, resource or budget grants, nor overwrite an advanced grant. Advanced scopes retain their existing native review path.

The same owner can now manage the product and read the explicitly granted project without switching accounts. An ungranted or different project remains denied. Details/coverage and selected context, identity, cost, runtime, attempt, capability, policy or destination metadata are independent of body reading. This page always leaves body reading disabled. Existing grants form a union: this editor cannot narrow another grant. Revoking its grant removes only that grant's access. A separate ordinary reader remains useful for checking least-privilege behavior.

Backup and restore

Use the complete private native backup. Schema47 private bundles use the version2 manifest and bind account authority, credential/revision rows and activation-ticket rows to server-side digests; no credential values appear in a receipt. Recovery preserves those rows, stable subjects, existing grants and audit history. Before activation, the restored database retires all pre-restore activation/recovery links using the exact restore operation's receipt. A previously spent link cannot be revived from an older snapshot. Request a new recovery link when needed. Resume recognizes a committed retirement even if its journal-completion write was interrupted, while unrelated authority changes remain an integrity failure.

For a business-data backup that predates account authority, native recovery retains the current initialized database accounts in the empty forward-migrated target; it never takes current credentials from the obsolete host file. The business grants and facts remain those of the selected backup. A genuine pre-schema47 installation is initialized from its validated legacy file once. Review those different recovery states before execution. Source and destination databases are preserved until the existing approved retirement procedure permits removal.

Connection synchronization (FPV20 / schema46)

On Connectors, each UR installation has an Auto sync preference and a local status view. New connections start in manual mode. Upgrade preserves existing Auto preferences and existing worker intervals. To quiet a test connection, identify that exact installation and explicitly switch its Auto sync off; upgrading does not pause every connection.

Auto sync controls XI outgoing Feed, source facts/events, current runtime, content, budgets and enrollment/capability maintenance for that connection. Saving a new interval accepts whole seconds from 5 through 3600; newly enabled connections default to 60 seconds. It is a minimum polling interval: original retry backoff and controller maintenance may take longer. Existing configured intervals remain in effect until a new interval is saved. Opening or refreshing a status page does not trigger a UR fetch. Local retention, expiry, audit and historical reading continue.

Sync once requires Auto sync off. It advances the applicable categories fairly and stops each category at its observed boundary. The whole run is bounded by 60 seconds, 32 data/control pages and 64 application HTTP attempts, including capability requests and failed attempts. It never enables Auto sync or resumes automatically after restart. Empty, completed, partial, error, cancelled, expired and interrupted outcomes have different meanings. A partial outcome is not proof of complete source coverage. A new attempt is an explicit new action. A lost response retains the original request locally; confirm that same request or refresh local status before starting another.

Stop sync changes the durable revision first. Already admitted work can remain in flight. The effective state stays stopping or unknown until the relevant worker completion is known. A timeout or missing worker heartbeat does not establish quiet. Results from a superseded revision cannot advance a database cursor or publish new collection state. Evidence committed before the stop remains retained and can be safely deduplicated when collection resumes.

The original Connect consent has a single bounded initialization continuation; it does not set Auto sync. A replayed ACK cannot renew it. If either product's bounded setup run completes before the other product is ready, the connection remains pending rather than being reported complete. Resume the required local action explicitly. XI can resume its own outgoing synchronization from its UI or CLI while its listener remains available. UR must resume its own control polling from its local UI or CLI. XI's quiet state is not evidence of UR quiet, and no cross-admin credentials or hidden remote wake are introduced.

Pause does not revoke authorization, clear a requires-attention condition or reset a cursor. If source retention expires, the gap remains visible and the existing explicit recovery procedure still applies. Last outgoing check and last data commit are shown separately; neither guarantees full source coverage.

An explicit delegated policy save uses its existing human account and immutable operation reference for a separate bounded control call (60 seconds / 32 pages / 64 attempts). It leaves Auto off and grants no collection worker permission. An unconfirmed result can be read within that original remaining budget; replay does not extend it. A terminal result is read locally. After the budget expires, use an explicit Sync once for remote recovery, retaining the original policy operation reference. Live policy discovery/read pages also require Auto or Sync once; opening those pages does not grant an implicit control run. Credential recovery keeps its existing human confirmation ticket and inbound protocol. At most 32 finite receipts are retained; a failed policy preflight receipt cannot be evicted until the original durable policy operation protects its identity. If that bound cannot be maintained, a new run fails closed.

The local administrator can use xinsightctl connector-sync status|auto-off|auto-on|once --installation-id ID --actor SUBJECT. Use the exact ID and an existing authorized local account subject. Changes require the observed --expected-revision and a stable UUID --request-id; Auto-on may specify --cadence-seconds. A retry reuses the original body and UUID. Do not start another task while the previous outcome is unconfirmed.

This candidate has a new schema and artifact identity. Local tests do not establish CI, signed distribution, installation or Target acceptance. Frozen FPV19 artifacts and signing inputs retain their original identities.
